# pytest-api-framework 技术文档

## 第1节：项目概览与架构说明

---

## 1.1 项目简介

### 1.1.1 框架目标

`pytest-api-framework` 是一个面向 **TakeoutSystem 外卖点餐系统** 的综合自动化测试框架，旨在通过统一的工程化手段覆盖从后端接口到前端交互的全链路测试需求。框架的核心设计目标有以下几点：

1. **接口与 UI 测试双覆盖**：在同一个框架内同时支持 HTTP 接口自动化（通过 `requests`）和浏览器 UI 自动化（通过 `selenium`），避免接口层和 UI 层维护两套独立的测试基础设施。

2. **Mock/真实双模式切换**：通过 `common/mock_util.py` 及命令行参数控制，测试可在不依赖真实后端服务的 **Mock 模式**与对接真实后端的**真实模式**之间无缝切换。这一设计让框架在 CI/CD 流水线（不启动后端）和本地联调（对接真实后端）两种场景下均可稳定运行。

3. **插件化扩展架构**：基础 HTTP 请求封装内置插件系统，支持熔断器、限流器、日志、Allure 附件等能力的按需启用/禁用，方便在不修改核心代码的情况下扩展测试基础设施能力。

4. **生产级可靠性机制**：框架引入了熔断器（Circuit Breaker）和限流器（Rate Limiter）等生产级可靠性模式，使得测试本身能够感知并应对后端服务的不稳定状况，避免雪崩式失败。

5. **数据与代码分离**：所有测试数据存放于 YAML 文件，通过 `yaml_util.py` 统一加载，测试用例逻辑不硬编码数据，便于数据的独立维护与多环境适配。

### 1.1.2 被测系统简介

**TakeoutSystem** 是一个完整的外卖点餐平台，采用前后端分离架构：

- **后端**：Spring Boot，提供 RESTful API，运行于 `localhost:8080`
- **前端 H5 用户端**：Vue 3 + Vant 组件库，运行于 `localhost:3001`，供普通消费者浏览商家、下单、支付、评价
- **前端商家端**：Vue 3 + Element Plus，运行于 `localhost:3002`，供商家管理商品和处理订单
- **前端管理后台**：Vue 3 + Element Plus，运行于 `localhost:3003`，供平台管理员管理商家资质等

系统涵盖的业务模块包括：用户认证与注册、商家信息管理、商品分类与详情、购物车管理、订单全流程（创建/支付/取消）、评价体系、优惠券与收藏夹，以及平台健康检查接口。业务链路完整，适合作为综合性测试框架的练兵目标。

### 1.1.3 框架特色

| 特色                   | 说明                                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------- |
| **双模式测试**         | `--mock` 命令行参数一键切换 Mock/真实模式，CI 无需依赖后端即可运行全量测试                           |
| **插件化 HTTP 客户端** | `base_requests.py` 内置插件钩子，熔断、限流、日志、Allure 附件均以插件形式挂载，核心代码零侵入       |
| **熔断器与限流器**     | 内置生产级故障保护机制，防止后端不稳定时测试套件雪崩式全量失败                                       |
| **Allure 深度集成**    | 自动将每次 HTTP 请求/响应以附件形式写入 Allure 报告，测试报告具备完整的接口调用链路追踪              |
| **多端 UI 覆盖**       | page_objects 按业务端（H5、商家端、管理后台）分组，Selenium 4 WebDriver 支持 mobile/desktop 两种视口 |
| **安全脱敏**           | `security.py` 对日志和报告中的敏感信息（密码、token）进行自动过滤，避免测试日志泄露凭据              |
| **xfail/xpass 治理**   | 针对后端尚未实现的功能和已知 Bug 使用 `xfail` 标注，区分"预期失败"与"意外通过"，报告更清晰           |

### 1.1.4 适合的使用场景

- **本地开发联调**：开发人员在本地启动后端后，以真实模式运行 API 测试，快速验证接口改动的正确性。
- **CI/CD 流水线**：后端未部署时，以 Mock 模式运行全量测试，用于门禁检查框架本身和业务逻辑的正确性。
- **版本回归测试**：在 TakeoutSystem 发布新版本前，以真实模式运行 66 个测试用例进行全面回归验证。
- **前端联调验证**：UI 测试覆盖 H5、商家端、管理后台三个前端应用，可在前端迭代后快速验证核心用户交互流程。
- **测试框架学习参考**：框架工程化程度较高，可作为学习 pytest 高阶用法（插件、fixture、parametrize、xfail、conftest）和 Selenium Page Object 模式的参考实现。

### 1.2.2 插件系统内部架构

```
base_requests.py._send()
        │
        ├─ [before_request 钩子]
        │       │
        │       ├── LoggingPlugin.before_request()  → 记录请求日志
        │       ├── CircuitBreakerPlugin.before_request()  → 检查熔断状态
        │       └── RateLimiterPlugin.before_request()  → 检查限流配额
        │
        ├─ requests.Session.request()  ← 实际 HTTP 发送（或 mock 拦截）
        │
        ├─ [after_response 钩子]
        │       │
        │       ├── CircuitBreakerPlugin.after_response()  → 更新成功计数
        │       ├── AllurePlugin.after_response()  → 附加请求/响应到 Allure
        │       └── LoggingPlugin.after_response()  → 记录响应日志（含脱敏）
        │
        └─ [on_error 钩子]
                │
                ├── CircuitBreakerPlugin.on_error()  → 更新失败计数，触发熔断
                └── LoggingPlugin.on_error()  → 记录异常详情

插件生命周期管理（PluginManager）：
┌─────────────────────────────────────────────────┐
│  PluginManager（单例，线程安全 Lock）              │
│                                                 │
│  _core_plugins: Dict[str, CorePlugin]           │  ← 核心插件，不可禁用
│  _plugins:      Dict[str, Plugin]               │  ← 普通插件，可动态启用/禁用
│                                                 │
│  register(plugin)   → 注册插件实例               │
│  enable(name)       → 启用普通插件               │
│  disable(name)      → 禁用普通插件               │
│  dispatch(hook, **kwargs) → 按优先级分发钩子      │
└─────────────────────────────────────────────────┘
```

### 1.4.2 各依赖详细说明

#### pytest 9.1.1

pytest 是本框架的测试运行时和组织中心。选择 9.x 版本的原因：

- **fixture 作用域**：支持 `session`/`module`/`class`/`function` 四级作用域，允许在 session 级别维护登录 token，避免每个测试用例重复登录。
- **参数化**：`@pytest.mark.parametrize` 结合 YAML 数据，可轻松实现数据驱动测试。
- **xfail/xpass 机制**：对已知 Bug 或未实现功能使用 `@pytest.mark.xfail`，区分"预期失败"与"意外通过"，使报告质量更高。
- **conftest.py 多层级**：根目录的 `conftest.py` 提供全局 fixture，`test_cases/web/conftest.py` 提供 WebDriver 局部 fixture，层级清晰。
- **命令行参数扩展**：通过 `pytest_addoption` 钩子注册 `--mock` 和 `--env` 参数，将测试模式控制集成到 CLI 调用。
- **Markers 系统**：`pytest.ini` 中注册 `smoke`/`regression`/`api`/`ui`/`mock` 等 marker，支持按场景筛选执行测试子集。

#### requests

requests 是框架 HTTP 层的底层实现。在 `base_requests.py` 中被封装为带插件系统的高阶客户端：

- 使用 `requests.Session` 而非裸 `requests.get()`，保留 cookie 和 header 的会话状态，支持登录后的连续多步接口测试。
- 所有请求参数（headers、timeout、verify）在 `config.py` 中统一配置，避免每次调用散落硬编码值。
- 响应对象在 `after_response` 钩子中被传递给各插件，由 `allure_plugin` 提取并附加到报告，由 `logging_plugin` 记录到日志文件。

#### selenium 4.x

selenium 4 相比 selenium 3 的关键改进：

- **Relative Locators**：支持基于相对位置（near/above/below/to_left_of）的元素定位，辅助应对 Vue 动态渲染的 DOM 结构。
- **Chrome DevTools Protocol (CDP)**：可直接操作浏览器底层，支持 localStorage/sessionStorage 的读写，框架用此实现 **token 注入**——测试初始化时直接写入 `localStorage.token`，跳过耗时的 UI 登录流程。
- **WebDriver Manager 兼容**：selenium 4 的 `webdriver.Chrome(service=Service(...))` API 与 `webdriver-manager` 兼容，可自动下载匹配的 ChromeDriver。

在本框架中，Selenium 的核心使用模式是 **Page Object Model (POM)**：页面的元素定位和操作逻辑全部封装在 `page_objects/` 中，测试用例只调用语义化的方法（如 `login_page.login("13800000003", "123456")`），与 DOM 细节解耦。

#### allure-pytest

allure-pytest 提供 pytest 与 Allure 报告框架的集成：

- 测试用例通过 `@allure.feature` / `@allure.story` / `@allure.title` 装饰器声明报告层级，生成按业务模块组织的测试报告。
- `api/base_api.py` 中的每个 API 方法通过 `@allure.step` 在报告中呈现为可展开的步骤节点。
- `allure_plugin.py` 在每次 HTTP 请求完成后，自动将请求体、响应体以 JSON 附件形式附加到对应测试步骤，无需手动 `allure.attach()`。
- UI 测试失败时，`base_page.py` 自动截图，并通过 `allure.attach()` 将截图嵌入报告。

运行报告的标准命令：

```bash
# 执行测试并生成 Allure 原始结果
pytest --alluredir=reports/allure_results

# 启动 Allure 报告服务
allure serve reports/allure_results
```

#### PyYAML

测试数据通过 YAML 文件管理，核心优势：

- **可读性强**：YAML 比 JSON 更适合人工维护，支持注释，适合测试工程师直接编辑。
- **多层嵌套**：`api_test_data.yaml` 按模块（auth/merchant/product/cart/order...）分节，每节内按场景（valid_login/invalid_login/boundary...）分组，结构清晰。
- **parametrize 集成**：`yaml_util.py` 加载数据后返回 Python dict/list，直接传入 `@pytest.mark.parametrize`，实现完整的数据驱动。

`api_test_data.yaml` 覆盖的数据分类：

| 数据分类    | 说明                                       |
| ----------- | ------------------------------------------ |
| auth        | 登录/注册/登出的有效和无效凭据             |
| merchant    | 商家列表查询、商家详情参数                 |
| product     | 商品分类、商品详情、价格边界值             |
| cart        | 添加购物车、修改数量、清空购物车           |
| order       | 创建订单所需地址、备注等参数               |
| payment     | 支付方式、金额数据                         |
| review      | 评分、评价内容（含边界值和 XSS 数据）      |
| coupon      | 优惠券码、折扣金额                         |
| favorite    | 商家 ID 列表                               |
| boundary    | 空值、超长字符串、特殊字符等边界值         |
| security    | SQL 注入、XSS、Path Traversal 安全测试数据 |
| performance | 批量请求参数                               |

#### python-dotenv

`.env` 文件用于本地覆盖配置，典型用途：

```ini
# .env（不提交 Git）
BASE_URL=http://localhost:8080
MOCK_MODE=false
TEST_PASSWORD=123456
LOG_LEVEL=DEBUG
```

`config.py` 在模块加载时调用 `load_dotenv()`，使 `.env` 中的键值覆盖系统环境变量。这样，CI/CD 流水线通过系统环境变量传入配置，开发者本地通过 `.env` 文件自定义，两套机制无缝兼容。

#### Faker

Faker 用于生成真实感的随机测试数据，在以下场景使用：

- 注册新用户时生成随机手机号，避免因手机号重复而导致测试失败。
- 生成随机收货地址（省市区、详细地址），提高地址相关接口的测试覆盖面。
- 生成随机评价内容，测试评价接口的字符集处理能力。

Faker 在 `conftest.py` 中初始化为 `fixture`，测试用例通过依赖注入使用，保证每次运行的随机数据可追溯（Faker 支持固定 `seed` 复现特定数据集）。

# 第二章 配置层（config/）

## 2.1 设计思路

### 为什么用环境变量 + .env 文件的方式

测试框架需要在不同环境（本地开发、CI/CD、预发布、生产灰度）下运行，每个环境的后端地址、认证账号、超时阈值各不相同。硬编码这些值会导致代码频繁改动，甚至将敏感信息（手机号、密码、token）提交到版本库。

本框架采用"环境变量优先、.env 文件兜底"的分层策略：

1. **运行时环境变量**（最高优先级）：CI/CD 系统（如 GitHub Actions）通过 `env:` 块注入，无需在磁盘上存储敏感信息。
2. **.env 文件**（本地开发兜底）：开发者在本地创建 `.env` 文件覆盖默认值，该文件通过 `.gitignore` 排除在版本库之外。
3. **代码默认值**（最低优先级）：`os.getenv("KEY", "default_value")` 中的第二参数，保证框架在零配置时也能运行（通常指向本地 `localhost`）。

`python-dotenv` 库的 `load_dotenv()` 在模块导入时执行一次，将 `.env` 文件中的键值对写入进程环境变量，此后所有 `os.getenv()` 调用均能感知到这些值。

### 多环境继承设计（Config 基类 → 子类）

```
Config（基类，持有所有默认值）
  ├── DevConfig    — 开发环境：DEBUG 日志、超长超时、关闭无头模式
  ├── TestConfig   — 测试环境：DEBUG 日志，其余继承基类
  ├── StagingConfig — 预发布：INFO 日志、强制无头浏览器
  └── ProdConfig   — 生产灰度：WARNING 日志、强制 SSL 校验、无头浏览器
```

Python 类继承确保子类只需声明与基类不同的字段，其余字段自动从 `Config` 继承。`get_config(env)` 工厂函数根据 `ENV` 环境变量返回对应子类实例，调用方无需感知具体环境类名。

### 配置验证的意义

错误的配置（如拼写错误的 URL、为零的超时值）往往在测试运行到一半时才暴露，导致难以定位的失败。`validate()` 方法在 `get_config()` 返回实例之前统一检查，将配置错误提升到进程启动阶段，快速失败、快速反馈。

## 2.5 配置验证机制

`Config.validate()` 是一个类方法，在 `get_config()` 工厂函数返回实例之前调用，任何验证失败都会抛出 `ConfigValidationError` 异常（继承自 `Exception`），携带所有错误的换行拼接信息。

### 验证项目详情

| 验证项               | 验证逻辑                                         | 错误示例                               |
| -------------------- | ------------------------------------------------ | -------------------------------------- |
| `API_BASE_URL` 格式  | 正则匹配 `http(s)://` + 合法主机名/IP + 可选端口 | `API_BASE_URL 格式无效: ftp://bad-url` |
| `API_TIMEOUT` 正整数 | `<= 0` 则报错                                    | `API_TIMEOUT 必须大于 0`               |
| `API_TIMEOUT` 上限   | `> 300` 则报错（防止误配置超长等待）             | `API_TIMEOUT 过大`                     |
| `BROWSER` 合法值     | 必须是 `chrome / firefox / edge / safari` 之一   | `BROWSER 必须是 [...] 之一`            |
| `ENVIRONMENT` 合法值 | 必须是 `dev / test / staging / prod` 之一        | `ENVIRONMENT 必须是 [...] 之一`        |

### URL 正则说明

```python
r'^https?://(localhost|(\d{1,3}\.){3}\d{1,3}|([a-zA-Z0-9-]+\.)+[a-zA-Z]{2,})(:\d+)?(/.*)?$'
```

该正则接受三种主机格式：

- `localhost`
- IPv4 地址（如 `192.168.1.100`）
- 域名（如 `api.example.com`）

端口号和路径前缀均为可选。`http://` 和 `https://` 均被接受。

### 错误收集策略

`validate()` 不在第一个错误处立即抛出，而是将所有错误先收集到 `errors` 列表，最后一次性抛出。这样配置存在多处错误时，开发者可以一次看到所有问题，而不必反复启动框架逐个修复。

### 使用示例

```python
from config.config import get_config, ConfigValidationError

try:
    cfg = get_config("prod")
except ConfigValidationError as e:
    print(f"配置错误，请检查环境变量：\n{e}")
    raise SystemExit(1)
```

# 第三章 HTTP 请求基类（common/base_requests.py）

## 3.1 设计思路

### 为什么要有 BaseRequests 而不直接用 requests 库

直接调用 `requests.get()` 能完成 HTTP 请求，但在自动化测试框架中存在以下不足：

1. **重试逻辑分散**：每个测试文件都需要自行处理 `503`、`429` 等临时性错误，代码重复。
2. **Allure 报告不统一**：`@allure.step` 装饰器需要在每个调用点手动添加，遗漏则报告缺失请求详情。
3. **插件无法注入**：缓存、熔断、限速、日志等横切关注点无法集中管理，只能硬编码在每个请求周围。
4. **Session 复用困难**：HTTP 连接池和认证 token 无法在同一个 client 实例中统一维护。

`BaseRequests` 封装了上述所有关注点，业务层只需调用 `self.get(endpoint)` 或 `self.post(endpoint, json=payload)`，不必关心底层细节。

### 插件系统集成点

`BaseRequests.__init__` 中通过 `get_plugin_manager()` 懒加载插件管理器。插件在 `_execute_with_plugins` 中被统一调用，有三个钩子触发点：

- `before_request`：请求发出前（可用于缓存命中、限速检查、熔断检查）
- `after_request`：请求成功返回后（用于 Allure 记录、缓存写入、指标统计）
- `on_request_error`：请求抛出异常时（用于错误日志、熔断计数）

`enable_plugins=False` 参数可在单元测试中跳过插件系统，避免引入额外依赖。

## 3.3 自动重试机制

`BaseRequests.__init__` 为 `requests.Session` 挂载了 `HTTPAdapter`，其中配置了 `urllib3.util.retry.Retry` 策略。

### Retry 参数说明

| 参数               | 值                                       | 含义                                                        |
| ------------------ | ---------------------------------------- | ----------------------------------------------------------- |
| `total`            | `3`（默认，可通过构造参数覆盖）          | 最大重试次数                                                |
| `backoff_factor`   | `1.0`（默认，可覆盖）                    | 指数退避基数                                                |
| `status_forcelist` | `[429, 500, 502, 503, 504]`              | 触发重试的 HTTP 状态码                                      |
| `allowed_methods`  | `HEAD/GET/PUT/DELETE/OPTIONS/TRACE/POST` | 允许重试的 HTTP 方法                                        |
| `raise_on_status`  | `False`                                  | 不自动将 4xx/5xx 转为异常（由 `_handle_response` 手动处理） |

### 退避时间计算公式

```
wait = backoff_factor * (2 ** (retry_number - 1))
```

以 `backoff_factor=1.0` 为例：

- 第 1 次重试等待：1.0 × 2^0 = **1 秒**
- 第 2 次重试等待：1.0 × 2^1 = **2 秒**
- 第 3 次重试等待：1.0 × 2^2 = **4 秒**

### 为什么 status_forcelist 包含 POST（幂等问题讨论）

从 HTTP 语义角度，`POST` 不是幂等操作，重试可能导致重复下单、重复扣款等副作用。然而在测试框架的使用场景下，我们做出了有意识的权衡：

- **测试环境的临时性错误频率更高**：CI/CD 中的后端服务有时因启动时序问题返回 `503`，此时重试是正确的。
- **测试数据可以清理**：与生产环境不同，测试数据库中的重复数据可以通过 fixture 清理，重复创建的影响可控。
- **真实 POST 调用量有限**：框架的 `USE_MOCK=true` 默认开启，大多数 `POST` 在 Mock 模式下根本不发出真实请求，重试策略对 Mock 模式无影响。

若在对接真实 API 时需要禁止 `POST` 重试，可在初始化时传入 `max_retries=0`，或继承 `BaseRequests` 覆盖 retry 策略。

## 3.4 插件钩子集成

### `_execute_with_plugins` 的工作原理

```python
def _execute_with_plugins(self, method, url, request_func, **kwargs):
    # 阶段1：before_request 钩子
    if self.plugin_manager:
        cached_results = self.plugin_manager.execute_hook('before_request', method, url, **kwargs)
        if cached_results:
            return cached_results[0]   # 短路返回
    try:
        # 阶段2：执行真实请求
        response = request_func()
        # 阶段3：after_request 钩子
        if self.plugin_manager:
            self.plugin_manager.execute_hook('after_request', response, method, url, **kwargs)
        return response
    except Exception as e:
        # 阶段4：on_request_error 钩子
        if self.plugin_manager:
            self.plugin_manager.execute_hook('on_request_error', e, method, url, **kwargs)
        raise
```

### before_request 返回非 None 时的短路逻辑（缓存场景）

`execute_hook('before_request', ...)` 会依次调用所有注册了该钩子的插件，并将非 `None` 的返回值收集到列表中。

当 **CachePlugin** 命中缓存时，它会返回缓存的 `response` 对象（非 `None`），`cached_results` 列表非空，`_execute_with_plugins` 立即返回 `cached_results[0]`，**跳过** `request_func()` 的调用。这意味着：

- 网络请求不会发出（节省时间，避免对后端造成额外压力）
- `after_request` 和 `on_request_error` 钩子**也不会触发**（因为走了短路路径）

如果没有任何插件在 `before_request` 阶段返回非 `None`，`cached_results` 为空列表，执行继续进入真实请求阶段。

### session 层 patch 的重要性（Mock 模式下 AllurePlugin 能正常触发的原因）

这是框架中一个关键的设计细节，详见第四章 4.3 节的深入解释。

## 3.5 session.headers 与认证

### 如何通过 session.headers 传递 Authorization token

`BaseRequests` 不直接管理认证，而是将其委托给上层的 Client 类（如 `CustomerApiClient`）。Client 类在登录后通过以下方式将 token 写入 session：

```python
# 在 CustomerApiClient.login() 中
self.session.headers.update({
    "Authorization": f"Bearer {token}"
})
```

此后该 Client 实例发出的所有请求都会自动携带该 Header，无需在每个 `get()`/`post()` 调用中手动传递。

### `_session_auth` 参数的作用（CachePlugin 用户隔离）

`get()` 方法中有一行：

```python
session_auth = self.session.headers.get("Authorization", "")
```

并将其作为 `_session_auth=session_auth` 传递给 `_execute_with_plugins`，最终流入插件钩子的 `kwargs`。

**CachePlugin 使用该值构造缓存键**：

```
cache_key = hash(method + url + params + _session_auth)
```

没有 `_session_auth` 的隔离，用户 A 的响应会被用户 B 命中，导致测试数据污染。例如：

- 消费者 A（token=`abc`）查询自己的订单列表 → 结果缓存
- 消费者 B（token=`xyz`）查询相同 endpoint → 错误命中 A 的缓存，返回 A 的订单

通过将 `Authorization` 值纳入缓存键，不同用户的相同请求会生成不同的缓存条目，完全隔离。

# 第四章 Mock 模式工具（common/mock_util.py）

## 4.1 Mock 模式的设计动机

### 为什么需要 Mock 模式

自动化测试框架在以下场景中需要脱离真实后端独立运行：

1. **后端服务未就绪**：前后端并行开发期间，后端接口尚未实现或尚未部署。
2. **CI/CD 环境无后端**：GitHub Actions 等 CI 环境通常不启动完整的 Spring Boot + MySQL 服务，搭建真实环境耗时且脆弱。
3. **测试隔离性**：真实 API 调用受网络状况、数据库状态影响，Mock 模式消除外部依赖，使测试结果稳定可重复。
4. **边界条件测试**：真实后端很难稳定复现 `500` 错误、超时、网络中断等场景；Mock 可以精确构造任意响应。
5. **测试速度**：跳过真实 HTTP 往返，大规模测试套件的运行时间可从数分钟缩短到数秒。

### Mock 模式 vs 真实 API 模式对比

| 维度         | Mock 模式（`USE_MOCK=true`） | 真实 API 模式（`USE_MOCK=false`） |
| ------------ | ---------------------------- | --------------------------------- |
| 后端依赖     | 不需要                       | 必须启动 Spring Boot 服务         |
| 数据库依赖   | 不需要                       | 需要 MySQL 数据初始化             |
| 运行速度     | 极快（毫秒级）               | 受网络和后端性能影响              |
| 测试稳定性   | 高，结果完全可控             | 受外部环境影响                    |
| Allure 报告  | 完整（插件正常触发）         | 完整                              |
| 边界条件覆盖 | 容易（手动构造响应）         | 困难（需后端配合）                |
| 真实集成验证 | 不验证                       | 验证完整调用链                    |
| 适用场景     | CI/CD、单元测试、开发期      | 集成测试、回归测试、验收测试      |

## 4.2 MockHelper 详解

### `use_mock` 属性读取逻辑

```python
class MockHelper:
    def __init__(self):
        self.use_mock = config.USE_MOCK
```

`config` 是模块级单例（在 `config.py` 末尾 `config = get_config()` 创建），`config.USE_MOCK` 读取的是 `os.getenv("USE_MOCK", "true").lower() == "true"` 的结果。

读取链路：

```
环境变量 USE_MOCK
    └─→ os.getenv("USE_MOCK", "true")
            └─→ .lower() == "true"  → bool
                    └─→ Config.USE_MOCK
                            └─→ config.USE_MOCK
                                    └─→ MockHelper.use_mock
```

将配置读取委托给 `config` 单例（而不是在 `MockHelper.__init__` 中直接调用 `os.getenv`）的好处是：

- 配置变更只需修改 `.env` 文件，无需触碰 `mock_util.py`
- 测试中可以通过 `mock.patch.object(config, 'USE_MOCK', False)` 动态切换模式

### `create_mock_response` 参数说明

```python
def create_mock_response(self, status_code=200, json_data=None, text="", headers=None):
```

| 参数          | 类型                     | 默认值 | 说明                                         |
| ------------- | ------------------------ | ------ | -------------------------------------------- |
| `status_code` | `int`                    | `200`  | HTTP 状态码，影响 `response.ok` 的值         |
| `json_data`   | `dict` / `list` / `None` | `{}`   | `response.json()` 的返回值                   |
| `text`        | `str`                    | `""`   | `response.text` 的返回值（用于非 JSON 响应） |
| `headers`     | `dict` / `None`          | `{}`   | `response.headers` 的返回值                  |

返回的 `Mock()` 对象模拟了 `requests.Response` 的常用属性：

```python
mock_response.status_code  # → int
mock_response.json()       # → dict/list（每次调用返回相同值）
mock_response.text         # → str
mock_response.headers      # → dict
mock_response.ok           # → bool（200 <= status_code < 300）
```

**常见使用示例：**

```python
mock = MockHelper()

# 正常响应
success = mock.create_mock_response(200, {"code": 1, "data": {"id": 123}})

# 认证失败
unauthorized = mock.create_mock_response(401, {"code": 0, "msg": "未登录"})

# 服务器错误
server_error = mock.create_mock_response(500, text="Internal Server Error")

# 带自定义 Header 的响应
with_headers = mock.create_mock_response(200, {"token": "abc"}, headers={"X-Auth-Token": "abc"})
```

### `mock_request` 上下文管理器工作原理

```python
@contextmanager
def mock_request(self, client, method, mock_response):
    if not self.use_mock:
        yield          # 真实 API 模式：什么都不做，直接执行 with 块内容
        return
    requests_obj = getattr(client, 'requests', client)
    session = getattr(requests_obj, 'session', None)
    target = session if session is not None else requests_obj
    with patch.object(target, method, return_value=mock_response):
        yield          # Mock 模式：patch session 的方法，with 块内所有调用返回 mock_response
```

**参数说明：**

| 参数            | 类型                    | 说明                                    |
| --------------- | ----------------------- | --------------------------------------- |
| `client`        | `BaseRequests` 子类实例 | 持有 `session` 的 HTTP Client           |
| `method`        | `str`                   | 要 patch 的方法名，如 `"get"`、`"post"` |
| `mock_response` | `Mock` 对象             | `create_mock_response()` 创建的模拟响应 |

**执行逻辑分支：**

```
mock_request(client, "get", mock_resp) 进入时
         │
         ├─ use_mock == False → yield（不 patch，真实请求会发出）
         │
         └─ use_mock == True
                  │
                  ├─ 获取 client.requests.session（若 client 有 requests 属性）
                  │   或直接用 client（若 client 本身就是 BaseRequests）
                  │
                  ├─ 获取 session 属性（BaseRequests 的 self.session）
                  │
                  └─ patch.object(session, "get", return_value=mock_resp)
                       → yield（with 块内 session.get() 返回 mock_resp）
                       → 退出时自动恢复原始 session.get
```

## 4.3 关键设计：在 session 层 patch 而非 BaseRequests 层

这是 Mock 工具中最重要的设计决策，理解它需要先了解 `_execute_with_plugins` 的调用栈。

### 早期版本的问题：在 BaseRequests.get/post 层 patch

早期版本的 `mock_request` 使用了如下 patch 目标：

```python
# 早期写法（有缺陷）
with patch.object(client, 'get', return_value=mock_response):
    yield
```

这将 `BaseRequests.get` 方法整体替换为一个直接返回 `mock_response` 的 lambda。

调用链变成：

```
client.get(endpoint)
    └─→ [被 patch 替换] → 直接返回 mock_response
         ↑
         BaseRequests.get 的原始实现被完全跳过！
         包括对 _execute_with_plugins 的调用也被跳过
```

**后果：**

- `_execute_with_plugins` 从未被调用
- `before_request` 钩子不触发（CachePlugin、CircuitBreaker 不生效）
- `after_request` 钩子不触发 → **AllurePlugin 不触发 → Allure 报告中无请求记录**
- Mock 模式和真实 API 模式下的插件行为完全不一致，Mock 测试通过并不能证明插件集成是正确的

### 修复后：在 session.get/post 层 patch

修复后的 patch 目标是 `session.get`（即 `requests.Session.get`）：

```python
# 修复后写法
session = getattr(requests_obj, 'session', None)
with patch.object(session, method, return_value=mock_response):
    yield
```

调用链变成：

```
client.get(endpoint)
    └─→ BaseRequests.get()          ← 正常执行，@allure.step 装饰器生效
            └─→ _execute_with_plugins()  ← 正常执行
                    ├─→ before_request 钩子触发  ← CachePlugin、CircuitBreaker 生效
                    ├─→ request_func()
                    │       └─→ session.get()    ← [被 patch 替换] → 返回 mock_response
                    │                              （不发真实 HTTP 请求）
                    └─→ after_request 钩子触发   ← AllurePlugin 记录请求详情 ✓
```

**修复效果：**

| 行为                         | 早期（patch BaseRequests.get） | 修复后（patch session.get） |
| ---------------------------- | ------------------------------ | --------------------------- |
| `@allure.step` 装饰器        | 不触发                         | 触发                        |
| `_execute_with_plugins` 执行 | 不执行                         | 执行                        |
| `before_request` 钩子        | 不触发                         | 触发                        |
| `after_request` 钩子         | 不触发                         | 触发                        |
| AllurePlugin 记录请求        | 无记录                         | 有完整记录                  |
| Mock 与真实模式行为一致性    | 不一致                         | 完全一致                    |
| 真实 HTTP 请求是否发出       | 不发出                         | 不发出                      |

### 设计原则总结

> **Mock 应该在最靠近网络的位置注入，而不是在业务逻辑层替换。**

`session.get` 是 `requests` 库中实际发起 TCP 连接的位置（往下是 urllib3），在这里 patch 相当于"截断网络"，而框架所有的业务逻辑（插件、日志、Allure 记录）都在其上层正常运行，行为与真实 API 模式完全一致。

这一设计使 Mock 测试不仅验证了业务逻辑，还验证了插件集成是否正确，显著提升了 Mock 测试的可信度。

## 4.4 在测试中使用 Mock 的标准模式

### 双模式写法规范

测试代码应同时支持 Mock 模式和真实 API 模式，通过 `mock.use_mock` 判断当前运行模式，分别准备响应。

```python
import pytest
import allure
from common.mock_util import MockHelper
from api.customer.customer_api import CustomerApiClient

mock = MockHelper()

class TestOrderCreation:
    """订单创建接口测试"""

    @pytest.fixture(autouse=True)
    def setup(self, base_url):
        self.client = CustomerApiClient(base_url)
        # 登录（Mock 模式下也走 mock_request）
        login_resp = mock.create_mock_response(200, {
            "code": 1,
            "data": {"token": "test-token-customer"}
        })
        with mock.mock_request(self.client, "post", login_resp):
            self.client.login("13800000003", "123456")

    @allure.title("正常下单 - 标准单商品订单")
    def test_create_order_success(self):
        # 1. 准备 Mock 响应（Mock 模式使用；真实模式由后端返回）
        success_response = mock.create_mock_response(
            status_code=200,
            json_data={
                "code": 1,
                "data": {
                    "id": 1001,
                    "status": "PENDING",
                    "totalAmount": 29.90
                }
            }
        )

        # 2. 双模式执行
        if mock.use_mock:
            # Mock 模式：patch session.post，拦截真实 HTTP 调用
            with mock.mock_request(self.client, "post", success_response):
                response = self.client.create_order({
                    "shopId": 1,
                    "items": [{"dishId": 101, "quantity": 2}],
                    "addressId": 1
                })
        else:
            # 真实 API 模式：直接调用，请求发往真实后端
            response = self.client.create_order({
                "shopId": 1,
                "items": [{"dishId": 101, "quantity": 2}],
                "addressId": 1
            })

        # 3. 断言（无论哪种模式，断言逻辑完全相同）
        assert response.status_code == 200
        data = response.json()
        assert data["code"] == 1
        assert data["data"]["id"] is not None
        assert data["data"]["status"] == "PENDING"

    @allure.title("下单失败 - 餐厅已打烊")
    def test_create_order_shop_closed(self):
        """测试边界条件：只有 Mock 模式能稳定复现此场景"""
        closed_response = mock.create_mock_response(
            status_code=400,
            json_data={"code": 0, "msg": "餐厅已打烊，暂不接单"}
        )

        if mock.use_mock:
            with mock.mock_request(self.client, "post", closed_response):
                response = self.client.create_order({
                    "shopId": 999,  # 已打烊的餐厅
                    "items": [{"dishId": 101, "quantity": 1}],
                    "addressId": 1
                })
        else:
            # 真实 API 模式需要后端数据库中存在已打烊餐厅
            pytest.skip("真实 API 模式需要特定后端数据，跳过此用例")

        assert response.status_code == 400
        assert response.json()["msg"] == "餐厅已打烊，暂不接单"
```

## 5.1 设计动机

### 为什么不把所有功能直接写在 common/ 里？

在框架早期设计阶段，最直接的做法是把日志记录、熔断器、限流器等功能直接写成工具函数或中间件，放在 `common/` 目录下，然后在 HTTP 客户端里逐一调用。这种方式看似简单，实则存在几个明显问题。

**直接封装的困境**

假设不用插件系统，HTTP 客户端代码会变成这样：

```python
# 直接封装方式（反面示例）
def request(self, method, url, **kwargs):
    logger.info(f"[请求前] {method} {url}")           # 日志
    circuit_breaker.check_state(url)                   # 熔断器检查
    rate_limiter.acquire()                             # 限流
    cache_result = cache.get(method, url, **kwargs)    # 缓存检查
    if cache_result:
        return cache_result

    try:
        response = self.session.request(method, url, **kwargs)
        circuit_breaker.record_success()               # 熔断器记录
        cache.set(method, url, response)               # 缓存写入
        logger.info(f"[请求后] {response.status_code}")
        allure_attach(response)                        # Allure附件
        return response
    except Exception as e:
        circuit_breaker.record_failure()
        logger.error(f"[请求错误] {e}")
        raise
```

问题显而易见：

- **高耦合**：HTTP 客户端直接依赖每一个功能模块，任何一个功能修改都可能影响客户端代码
- **不可扩展**：要新增一个"慢请求统计"功能，必须修改核心的 HTTP 客户端文件
- **无法按需禁用**：调试时想临时关掉 Allure 附件，需要修改代码或加 if 判断
- **职责混乱**：HTTP 客户端既要负责发请求，又要负责日志、熔断、限流、缓存，违反单一职责原则

**插件系统的优势**

| 对比维度      | 直接封装             | 插件系统                      |
| ------------- | -------------------- | ----------------------------- |
| 扩展新功能    | 修改核心代码         | 新建插件文件，注册即可        |
| 禁用某个功能  | 注释代码或加 if 标志 | `manager.disable("logging")`  |
| 测试某个功能  | 难以隔离             | 可单独测试插件逻辑            |
| 功能加载顺序  | 硬编码在函数体内     | 统一由 manager 按注册顺序调用 |
| 区分必选/可选 | 无法区分             | CorePlugin vs Plugin 类型隔离 |
| 线程安全      | 需每处手动处理       | 单例 manager 统一管理         |

插件系统把"何时做"（钩子时机）与"做什么"（插件逻辑）分离，HTTP 客户端只需在合适的时机调用 `execute_hook()`，不关心有哪些插件，也不关心每个插件做什么。

---

## 5.2 "硬逻辑 + 软钩子"设计模式

这是本框架插件系统的核心设计哲学，解决了一个根本问题：**哪些功能是系统稳定性的底线，不能被随意关闭？哪些功能是增强性的，可以按需启用？**

### 硬逻辑：核心插件（CorePlugin）

"硬"体现在两点：

1. **强制加载**：`get_plugin_manager()` 初始化时，核心插件通过 `force=True` 参数注册，即使同名插件已存在也会覆盖
2. **不可禁用**：`PluginManager.disable()` 检查到 `PluginType.CORE` 时直接返回 `False`，拒绝禁用操作

核心插件守护的是系统稳定性底线：

- **熔断器（CircuitBreakerPlugin）**：防止被测服务故障时，测试套件雪崩式失败，保护测试环境
- **限流器（RateLimiterPlugin）**：防止测试并发请求压垮被测服务，保护 TakeoutSystem 后端

即使通过命令行传入 `--disable-plugins circuit_breaker`，底层的 `disable()` 方法也会静默拒绝，并输出 warning 日志，核心插件始终处于工作状态。

### 软钩子：普通插件（Plugin）

"软"体现在可控性：

- **可禁用**：`plugin_type == PluginType.NORMAL` 的插件，可以通过 `manager.disable()` 切换到 `DISABLED` 状态
- **禁用后静默跳过**：`execute_hook()` 执行时，检查到插件状态不是 `ENABLED`，直接跳过该插件的钩子，不抛出异常
- **不影响核心流程**：普通插件的钩子即使全部禁用，HTTP 请求依然正常发出，测试依然正常运行

普通插件承载的是增强性功能：

- **LoggingPlugin**：调试时有用，CI 环境下有时希望减少日志噪音
- **AllurePlugin**：生成报告时需要，快速调试时不需要附件开销
- **MetricsPlugin**（未启用）：统计信息由 pytest 终端覆盖，不需要重复
- **CachePlugin**（未启用）：POST→GET 验证场景会读到缓存旧值，暂时不启用

### 设计对比图

```
     ┌─────────────────────────────────────────────┐
     │              HTTP 客户端请求流程              │
     └─────────────────────────────────────────────┘
                           │
          ┌────────────────┴────────────────┐
          │                                 │
     硬逻辑（必须执行）              软钩子（可选执行）
          │                                 │
  ┌───────────────┐              ┌─────────────────────┐
  │ CircuitBreaker │              │   LoggingPlugin     │
  │ RateLimiter   │              │   AllurePlugin      │
  │               │              │   MetricsPlugin(禁) │
  │ 不可 disable  │              │   CachePlugin(禁)   │
  └───────────────┘              └─────────────────────┘
```

## 5.3 类型体系

### 5.3.1 PluginState 枚举

插件在其生命周期中会经历四种状态：

```
LOADED ──────────────► ENABLED ──────────────► DISABLED
  │                                                │
  │     初始化完成          enable()     disable()  │
  │                                                │
  └──────────────────── ERROR ◄────────────────────┘
                   （钩子执行异常时记录，不自动切换）
```

| 状态       | 含义                             | 何时进入                                |
| ---------- | -------------------------------- | --------------------------------------- |
| `LOADED`   | 插件已注册到 manager，但尚未启用 | `register()` 调用后，`on_load()` 执行后 |
| `ENABLED`  | 插件正常工作，钩子会被执行       | `enable()` 调用后                       |
| `DISABLED` | 插件已禁用，钩子会被跳过         | `disable()` 调用后（仅 NORMAL 类型）    |
| `ERROR`    | 插件执行出错（预留状态）         | 当前实现中由外部记录，不自动转换        |

**关键点**：`execute_hook()` 中只执行状态为 `ENABLED` 的插件，`LOADED` 状态的插件也不会执行。因此注册后必须显式调用 `enable()` 才能让插件生效——这是框架中曾经存在的一个 bug 的根源（详见 5.4 节）。

### 5.3.2 PluginType 枚举

```python
class PluginType(Enum):
    CORE = "core"      # 核心插件：不可禁用
    NORMAL = "normal"  # 普通插件：可禁用
```

`PluginType` 直接决定了插件是否可以被 `disable()` 方法成功禁用。这个枚举通过插件子类来声明：继承 `CorePlugin` 的插件，其 `plugin_type` 属性固定返回 `PluginType.CORE`；直接继承 `Plugin` 的普通插件，默认返回 `PluginType.NORMAL`。

### 5.3.3 PluginInfo dataclass

```python
@dataclass
class PluginInfo:
    name: str
    version: str
    description: str
    author: str
    plugin_type: PluginType
    state: PluginState = PluginState.LOADED
```

`PluginInfo` 是插件的"身份证"，与插件实例分开存储在 `plugin_info` 字典中。这样做的好处是：状态变更只需修改 `PluginInfo.state`，不需要修改插件实例本身，插件实例保持无状态（除了各自的业务状态如熔断器计数、缓存数据等）。

两个计算属性的作用：

- `is_core`：等价于 `plugin_type == PluginType.CORE`，供外部判断时语义更清晰
- `can_disable`：等价于 `plugin_type == PluginType.NORMAL`，明确表达"是否允许禁用"的业务含义

### 5.3.4 Plugin 抽象基类

`Plugin` 定义了所有插件必须实现的接口和可选覆盖的钩子方法：

**必须实现**（`@abstractmethod`）：

- `name` → str：插件唯一标识，用作字典 key
- `version` → str：版本号，用于调试和日志

**可选覆盖**（默认空实现）：

- `description`、`author`：元信息
- `plugin_type`：默认 `NORMAL`，CorePlugin 子类覆盖为 `CORE`

**生命周期钩子**（默认空实现，无返回值）：

- `on_load()`：注册时调用，可做初始化工作
- `on_enable()`：启用时调用
- `on_disable()`：禁用时调用（CorePlugin 覆盖此方法输出 warning）
- `on_unload()`：卸载时调用，可做资源清理

**请求钩子（7个）**：

| 钩子方法                                         | 触发时机       | 短路语义                                     |
| ------------------------------------------------ | -------------- | -------------------------------------------- |
| `before_request(method, url, **kwargs)`          | 发送请求前     | 返回非 None 值则短路，跳过后续插件和真实请求 |
| `after_request(response, method, url, **kwargs)` | 请求成功后     | 无短路，仅通知                               |
| `on_request_error(error, method, url, **kwargs)` | 请求异常时     | 无短路，仅通知                               |
| `before_test(test_name)`                         | 测试用例开始前 | 无短路                                       |
| `after_test(test_name, result)`                  | 测试用例结束后 | 无短路                                       |
| `on_test_failure(test_name, error)`              | 测试断言失败时 | 无短路                                       |
| `on_test_success(test_name)`                     | 测试通过时     | 无短路                                       |

**`before_request` 的短路语义**详解：

`CachePlugin` 利用此机制实现缓存短路——当 `before_request` 返回缓存的 response 对象（非 None），`execute_hook` 将其收集进 results 列表，HTTP 客户端检查 results，若有返回值则直接用缓存结果，跳过真实的网络请求。这是插件系统中唯一的"控制流介入"机制，其余钩子均为纯通知型。

### 5.3.5 CorePlugin：如何阻止禁用

```python
class CorePlugin(Plugin):
    @property
    def plugin_type(self):
        return PluginType.CORE   # 固定返回 CORE

    def on_disable(self):
        logger.warning(f"核心插件 '{self.name}' 不允许禁用")
        # 注意：此处不抛出异常，由 manager.disable() 负责拦截
```

阻止禁用的逻辑实际上在两处都有防护：

1. `CorePlugin.on_disable()` 输出 warning（最后一道防线，语义提示）
2. `PluginManager.disable()` 检查 `plugin.plugin_type == PluginType.CORE`，直接 return False，不调用 `on_disable()`，也不修改状态（主防线）

因此即使有人绕过 `disable()` 直接调用 `plugin.on_disable()`，也只会得到一条 warning，状态依然是 `ENABLED`（因为状态存在 `PluginInfo` 中，不由 `on_disable()` 修改）。

## 5.4 插件管理器（PluginManager）

### 插件完整生命周期

```
  插件类                  PluginManager              PluginInfo.state
  ─────                  ─────────────              ───────────────

  MyPlugin()
      │
      │  register(plugin)
      ├─────────────────►  plugins[name] = plugin
      │                    plugin_info[name] = PluginInfo(...)   ──► LOADED
      │                    plugin.on_load()
      │                    _register_hooks(plugin)
      │
      │  enable(name)
      ├─────────────────►  plugin.on_enable()                    ──► ENABLED
      │
      │  execute_hook(...)
      ├─────────────────►  检查 state == ENABLED？
      │                    是 ──► 调用钩子函数
      │                    否 ──► 跳过
      │
      │  disable(name)
      ├─────────────────►  检查 plugin_type == CORE？
      │                    是 ──► return False（拒绝）
      │                    否 ──► plugin.on_disable()            ──► DISABLED
      │
      │  （卸载，当前未实现为公开接口）
      └─────────────────►  plugin.on_unload()                    ──► （移除）
```

### register() 详解

```python
def register(self, plugin, force=False):
    if plugin.name in self.plugins and not force:
        return   # 已注册且不强制，静默跳过
    self.plugins[plugin.name] = plugin
    self.plugin_info[plugin.name] = PluginInfo(
        name=plugin.name, version=plugin.version,
        description=plugin.description, author=plugin.author,
        plugin_type=plugin.plugin_type
    )
    plugin.on_load()
    self._register_hooks(plugin)
```

`force=True` 的使用场景：核心插件初始化时使用，确保即使有同名插件也会被核心插件覆盖，防止伪装成核心插件名字的恶意插件被保留。

### execute_hook() 的状态检查逻辑

```python
def execute_hook(self, hook_name, *args, **kwargs):
    results = []
    for hook_func in self.hooks[hook_name]:
        plugin_name = hook_func.__self__.name
        info = self.plugin_info.get(plugin_name)
        if info and info.state != PluginState.ENABLED:
            continue  # 关键：禁用的插件跳过
        try:
            result = hook_func(*args, **kwargs)
            if result is not None:
                results.append(result)
        except Exception as e:
            logger.error(f"执行钩子 '{hook_name}' 失败: {e}")
    return results
```

**为什么要检查 `PluginState.ENABLED` 而不是 `!= PluginState.DISABLED`？**

这是一个细节但很重要的区别。状态检查使用的是"白名单逻辑"（只有 ENABLED 才执行），而不是"黑名单逻辑"（只有 DISABLED 才跳过）。

考虑这种情况：插件注册后（状态为 `LOADED`），还没有调用 `enable()`，此时：

- 黑名单逻辑：`LOADED != DISABLED`，钩子会被执行 → **错误行为**
- 白名单逻辑：`LOADED != ENABLED`，钩子被跳过 → **正确行为**

**历史上的一个 bug**：框架早期版本曾使用过黑名单逻辑，导致刚注册但还未 enable 的插件就开始执行钩子。具体表现是：当 `get_plugin_manager()` 正在初始化，注册了熔断器插件但还没有调用 `enable()`，此时另一个线程发出了 HTTP 请求，触发 `execute_hook('before_request')`，熔断器插件由于状态是 `LOADED`（不是 DISABLED），黑名单逻辑允许其执行，但熔断器内部状态尚未完全初始化，导致 `AttributeError`。改为白名单逻辑后，`LOADED` 状态的插件被跳过，该问题消除。

**钩子执行异常的处理**：单个插件的钩子抛出异常，会被 `try/except` 捕获并记录日志，不影响其他插件的钩子执行，也不影响 HTTP 请求本身。这保证了插件的"增强性"特性——插件出问题不会导致测试用例失败。

## 5.5 线程安全单例（get_plugin_manager）

### double-check locking 原理

```python
_global_plugin_manager = None
_plugin_manager_lock = _threading.Lock()

def get_plugin_manager() -> PluginManager:
    global _global_plugin_manager
    if _global_plugin_manager is None:            # 第一次检查（无锁）
        with _plugin_manager_lock:                 # 获取锁
            if _global_plugin_manager is None:    # 第二次检查（有锁）
                manager = PluginManager()
                # ... 注册和启用所有插件 ...
                _global_plugin_manager = manager  # 最后赋值
    return _global_plugin_manager
```

**为什么需要两次检查？**

| 场景                    | 第一次检查        | 加锁     | 第二次检查    | 结果                |
| ----------------------- | ----------------- | -------- | ------------- | ------------------- |
| 首次调用，单线程        | None，进入        | 获取锁   | None，创建    | 正常创建            |
| 已初始化                | 非 None，直接返回 | 不加锁   | —             | 无锁快速返回        |
| 并发首次调用，线程A先到 | None，进入        | A 获取锁 | None，A 创建  | A 正常创建          |
| 并发首次调用，线程B后到 | None，也进入      | B 等待锁 | B 发现非 None | B 直接返回 A 的实例 |

如果只有第一次检查（不加锁），两个线程可能同时通过检查，各自创建一个 PluginManager，导致插件被注册两次。

如果只有加锁（无第一次检查），每次 `get_plugin_manager()` 调用都要竞争锁，在高并发测试场景下成为性能瓶颈。

双重检查锁定结合了两者优点：已初始化后的调用无需加锁，只有极少数"初始化竞争"时才加锁，且锁保护下的第二次检查防止重复创建。

### 为什么要在完全初始化后才赋值 \_global_plugin_manager？

```python
# 错误做法（过早赋值）
_global_plugin_manager = PluginManager()      # ← 赋值
manager.register(CircuitBreakerPlugin(...))    # ← 继续初始化
manager.register(LoggingPlugin())
# 如果此时另一个线程调用 get_plugin_manager()，
# 会拿到一个还没注册完插件的 manager！

# 正确做法（完整初始化后赋值）
manager = PluginManager()                      # ← 局部变量
manager.register(CircuitBreakerPlugin(...))
manager.register(LoggingPlugin())
for name in manager.plugins.keys():
    manager.enable(name)
_global_plugin_manager = manager               # ← 全部完成后才赋值
```

Python 的内存模型中，对象属性赋值不是原子操作，过早赋值会导致其他线程拿到"半成品"的 manager——插件只注册了一部分，某些插件未 enable，钩子列表不完整。将赋值放在最后，确保其他线程要么看到 `None`（继续等待锁），要么看到完全初始化好的 manager（直接使用）。

## 5.6 钩子执行顺序与时序

下面是一次完整测试请求中，各钩子的触发顺序（以启用了熔断器、限流器、日志、Allure 四个插件为例）：

```
测试用例开始
     │
     ▼
before_test(test_name)
     ├── LoggingPlugin: logger.info("[测试前] test_name")
     │
     ▼
before_request(method, url, **kwargs)
     ├── CircuitBreakerPlugin: 检查熔断器状态
     │       OPEN 且无法尝试重置 ──► 抛出 CircuitBreakerError，终止请求
     │       CLOSED / HALF_OPEN ──► return None，继续
     ├── RateLimiterPlugin: 令牌桶/滑动窗口检查
     │       超限 ──► wait() 阻塞等待，然后继续
     │       未超限 ──► acquire() 返回 True，继续
     └── LoggingPlugin: logger.info("[请求前] method url")
     │
     ▼
     ★ 实际 HTTP 请求（requests.Session.request()）
     │
     ├── 成功 ──────────────────────────────────────────────────────────────┐
     │                                                                      │
     ▼                                                                      │
after_request(response, method, url, **kwargs)                             │
     ├── CircuitBreakerPlugin: status_code < 500 ──► record_success()      │
     ├── LoggingPlugin: logger.info("[请求后] status_code")                 │
     └── AllurePlugin: 附加 Request JSON + Response JSON 到 Allure 报告    │
     │                                                                      │
     ├── 失败（网络异常/超时）◄────────────────────────────────────────────┘
     │
     ▼
on_request_error(error, method, url, **kwargs)
     ├── CircuitBreakerPlugin: record_failure()（累计失败次数）
     ├── LoggingPlugin: logger.error("[请求错误] error")
     └── AllurePlugin: 附加 Error 文本到 Allure 报告
     │
     ▼
（测试用例中的 assert 断言）
     │
     ├── 断言通过
     │       ▼
     │   on_test_success(test_name)
     │       └── LoggingPlugin: logger.info("[测试成功] test_name")
     │       ▼
     │   after_test(test_name, result="passed")
     │       └── LoggingPlugin: logger.info("[测试后] test_name | 结果: passed")
     │
     └── 断言失败
             ▼
         on_test_failure(test_name, error)
             └── LoggingPlugin: logger.error("[测试失败] test_name | error")
             ▼
         after_test(test_name, result="failed")
             └── LoggingPlugin: logger.info("[测试后] test_name | 结果: failed")
```

**注意**：`before_request` 中，熔断器和限流器排在日志插件之前（按注册顺序），这是有意设计的——熔断器如果拦截了请求，日志不应记录一条"请求前"日志（因为实际上请求没有发出）。若需调整顺序，修改 `get_plugin_manager()` 中的注册顺序即可。

## 5.7 六个插件逐一详解

### 5.7.1 CircuitBreakerPlugin（熔断器，核心插件）

**功能**：防止被测服务持续故障时，测试套件雪崩式失败（所有测试都在等待超时）。

**启用状态**：始终启用（CorePlugin，不可禁用）

**配置参数**：

- `failure_threshold=5`：连续失败 5 次后开启熔断
- `timeout=60`：熔断开启后，等待 60 秒进入半开状态

**实现的钩子**：

| 钩子               | 逻辑                                                             |
| ------------------ | ---------------------------------------------------------------- |
| `before_request`   | 检查熔断器状态，OPEN 且不能尝试重置时抛出 `CircuitBreakerError`  |
| `after_request`    | `status_code < 500` 时记录成功（5xx 视为服务端故障，不记录成功） |
| `on_request_error` | 网络异常时记录失败                                               |

**三态状态机**：

```
         失败次数 < threshold                   失败次数 >= threshold
  CLOSED ─────────────────────────────────────────────────────► OPEN
    ▲                                                              │
    │                                                     等待 timeout 秒
    │                                                              │
    │    下一次请求成功                                              ▼
    └───────────────────────────────────────────────────── HALF_OPEN
                                                   （允许一次探测请求）
                                                   探测失败 ──► 回到 OPEN
```

**熔断触发示例**：

```
测试1: GET /orders → 500 → record_failure() [1/5]
测试2: GET /orders → 500 → record_failure() [2/5]
...
测试5: GET /orders → 500 → record_failure() [5/5] → 熔断器 OPEN
测试6: before_request → 抛出 CircuitBreakerError
测试7: before_request → 抛出 CircuitBreakerError
...（60秒后）
测试N: before_request → 进入 HALF_OPEN，允许一次探测
```

---

### 5.7.2 RateLimiterPlugin（限流器，核心插件）

**功能**：控制单位时间内的请求频率，防止测试并发压垮 TakeoutSystem 后端服务。

**启用状态**：始终启用（CorePlugin，不可禁用）

**配置参数**：

- `max_calls=100`：窗口内最大请求次数
- `period=60.0`：滑动窗口大小（秒）

即：100次请求/60秒 ≈ 1.67次/秒的平均速率上限。

**实现的钩子**：

| 钩子             | 逻辑                                                                    |
| ---------------- | ----------------------------------------------------------------------- |
| `before_request` | 调用 `limiter.acquire()`，失败时调用 `wait()` 阻塞，返回 None（不短路） |

**acquire() 与 wait() 的行为**：

`acquire()` 尝试从滑动窗口内"申请"一个请求配额：

- 成功（窗口内计数 < max_calls）：直接返回 True，请求继续
- 失败（窗口内已满）：返回 False

`wait()` 在 acquire() 失败时调用，计算出窗口中最旧的请求将在何时过期，精确等待那段时间，然后自动重试。这是"阻塞等待"而非"丢弃请求"，因为测试框架中所有请求都应该最终得到执行（只是被限速，不是被丢弃）。

---

### 5.7.3 LoggingPlugin（日志插件，普通插件，已启用）

**功能**：为每个请求和测试用例自动添加结构化日志，无需在测试代码中手动添加日志语句。

**启用状态**：已启用（可通过 `disable("logging")` 禁用）

**实现的钩子**：7个钩子全部实现（框架中唯一实现全部7个钩子的插件）

**输出格式示例**：

```
INFO  [测试前] test_create_order
INFO  [请求前] POST http://localhost:8080/user/order
INFO  [请求后] POST http://localhost:8080/user/order | 状态: 200
INFO  [测试成功] test_create_order
INFO  [测试后] test_create_order | 结果: passed

ERROR [请求错误] POST http://localhost:8080/user/order | 错误: ConnectionError
ERROR [测试失败] test_create_order | 错误: AssertionError: Expected 200, got 500
```

**设计说明**：LoggingPlugin 只做日志输出，不对请求或响应做任何修改，所有钩子方法均无返回值（不触发短路）。日志级别的选择：正常流程用 `INFO`，错误和失败用 `ERROR`，这与标准日志实践一致，便于过滤日志级别。

---

### 5.7.4 AllurePlugin（Allure 附件插件，普通插件，已启用）

**功能**：自动将每次 HTTP 请求的请求详情和响应详情以 JSON 格式附加到 Allure 测试报告中，无需在测试代码中手动调用 `allure.attach()`。

**启用状态**：已启用（可通过 `disable("allure_attachment")` 禁用）

**实现的钩子**：

| 钩子               | 逻辑                                             |
| ------------------ | ------------------------------------------------ |
| `after_request`    | 生成 Request JSON + Response JSON，附加到 Allure |
| `on_request_error` | 附加错误信息文本                                 |

**附件命名规则**：

```python
endpoint = url.rstrip("/").rsplit("/", 1)[-1]
# url = "http://localhost:8080/user/order/123"
# endpoint = "123"
# 附件名 = "Request  POST /123"

# url = "http://localhost:8080/user/login"
# endpoint = "login"
# 附件名 = "Request  POST /login"
```

**Request JSON 附件内容示例**：

```json
{
  "method": "POST",
  "url": "http://localhost:8080/user/order",
  "body": {
    "addressBookId": 1,
    "amount": 38.5
  }
}
```

**Response JSON 附件内容示例**：

```json
{
  "status_code": 200,
  "body": {
    "code": 1,
    "msg": null,
    "data": 1001
  }
}
```

**为什么在插件层做附件，而不是在测试层做？**

如果在每个测试用例里手动添加 `allure.attach(response.text)`，会导致：

1. 大量测试代码重复（每个测试都要写 `allure.attach` 逻辑）
2. 忘记添加时报告缺失信息
3. 附件格式不统一

通过 AllurePlugin 的 `after_request` 钩子，所有经过 HTTP 客户端的请求都会自动附加，测试代码保持干净，报告内容完整一致。

**响应体的安全处理**：

```python
try:
    response_info["body"] = response.json()  # 优先解析 JSON
except:
    response_info["body"] = response.text[:500]  # 非JSON则截取文本前500字符
```

这防止了二进制响应或超大响应体导致的附件问题。

---

### 5.7.5 MetricsPlugin（指标统计插件，普通插件，未启用）

**功能**：统计测试运行过程中的各类指标：请求总数、成功/失败数、测试总数、通过/失败数、运行时长。

**启用状态**：代码已保留，但 `get_plugin_manager()` 中未注册，因此不会生效。

**收集的指标**：

```python
metrics = {
    'request_count': 0,      # 总请求数
    'request_success': 0,    # 成功请求数（status_code < 400）
    'request_failed': 0,     # 失败请求数（status_code >= 400）
    'test_count': 0,          # 总测试数
    'test_passed': 0,         # 通过测试数
    'test_failed': 0,         # 失败测试数
    'start_time': None,       # 开始时间
    'end_time': None          # 结束时间
}
```

**为什么不启用？**

pytest 本身在测试运行结束后会输出如下统计：

```
====== 42 passed, 3 failed in 18.34s ======
```

Allure 报告也提供了通过率、用时等统计图表。MetricsPlugin 提供的统计与这些工具高度重叠，启用它会增加钩子执行开销，却没有额外价值。

**保留代码的原因**：在需要将指标上报到监控系统（如 Prometheus、InfluxDB）时，可以在 `get_summary()` 中添加上报逻辑，然后在 `get_plugin_manager()` 中取消注释即可启用。

---

### 5.7.6 CachePlugin（GET 缓存插件，普通插件，未启用）

**功能**：缓存 GET 请求的响应，相同请求第二次调用时直接返回缓存结果，减少对被测服务的请求次数。

**启用状态**：代码已保留，但 `get_plugin_manager()` 中未注册。

**缓存 key 的构成**：

```python
def _get_cache_key(self, method, url, **kwargs):
    auth = kwargs.get("_session_auth", "")   # 用户标识
    params_str = str(kwargs.get("params", ""))
    return f"{method}_{url}_{auth}_{params_str}"
```

缓存 key 包含四个维度：
| 维度 | 作用 |
|------|------|
| `method` | 只有 GET 请求才写入缓存（before_request 中检查） |
| `url` | 区分不同接口 |
| `_session_auth` | 区分不同用户（admin 和普通用户看到的数据不同） |
| `params` | 区分相同接口但参数不同的请求（如分页、过滤条件） |

**\_session_auth 实现用户级缓存隔离**：

如果不区分用户，用户 A 查询自己的订单列表，会被用户 B 用同一个缓存 key 命中，拿到用户 A 的数据——这在权限验证测试中会导致假阳性（本该失败的测试通过了）。`_session_auth` 是在调用 HTTP 客户端时注入的用户标识（如 token 的哈希值），确保不同用户的相同请求有独立的缓存空间。

**为什么不启用？**

外卖系统测试中大量使用"POST 操作 → GET 验证"的模式：

```python
# 创建订单
response = client.post("/user/order", json=order_data)
order_id = response.json()["data"]

# 验证订单存在
response = client.get(f"/user/order/{order_id}")   # ← 这里会命中缓存？
assert response.json()["data"]["status"] == 0
```

如果在 POST 之前已经请求过 `GET /user/order/{order_id}`（比如在 fixture 中），缓存中会存在旧值（通常是 404 或空数据）。POST 创建后再次 GET，`CachePlugin` 会返回旧的缓存值，导致测试断言失败——实际上服务是正确的，是缓存干扰了结果。

此外，TTL 设为 300 秒，在一个测试套件运行期间（通常 5-20 分钟），数据可能已经通过其他测试用例被修改，但缓存不感知这些变化。

## 5.8 扩展：如何自己写一个插件

下面通过一个完整示例演示如何自定义插件——统计响应时间超过 1 秒的慢请求，并在测试结束时输出汇总报告。

### 示例：SlowRequestPlugin

在 `common/plugins/` 目录下新建文件 `slow_request_plugin.py`：

```python
# common/plugins/slow_request_plugin.py

import time
import logging
from typing import List, Dict
from .base import Plugin, PluginType

logger = logging.getLogger(__name__)


class SlowRequestPlugin(Plugin):
    """
    慢请求统计插件：记录响应时间超过阈值的请求，并输出汇总报告。
    这是一个普通插件（NORMAL），可以通过 disable("slow_requests") 禁用。
    """

    def __init__(self, threshold_ms: float = 1000.0):
        """
        :param threshold_ms: 慢请求阈值，单位毫秒，默认 1000ms（1秒）
        """
        self.threshold_ms = threshold_ms
        self.slow_requests: List[Dict] = []   # 慢请求记录列表
        self._request_start_times: Dict[str, float] = {}  # 请求开始时间

    @property
    def name(self) -> str:
        return "slow_requests"

    @property
    def version(self) -> str:
        return "1.0.0"

    @property
    def description(self) -> str:
        return f"统计响应时间超过 {self.threshold_ms}ms 的慢请求"

    @property
    def author(self) -> str:
        return "your-name"

    def on_enable(self):
        logger.info(f"[SlowRequestPlugin] 慢请求阈值: {self.threshold_ms}ms")

    def before_request(self, method: str, url: str, **kwargs):
        """在请求开始前记录时间戳。"""
        # 用 (method, url) 作为 key 记录开始时间
        # 注意：并发场景下同一 url 可能有多个请求，简单场景此处够用
        key = f"{method}_{url}"
        self._request_start_times[key] = time.time()
        return None  # 不短路，继续执行后续钩子和真实请求

    def after_request(self, response, method: str, url: str, **kwargs):
        """在请求结束后计算耗时，超阈值则记录。"""
        key = f"{method}_{url}"
        start_time = self._request_start_times.pop(key, None)
        if start_time is None:
            return  # 没有开始时间记录，跳过

        elapsed_ms = (time.time() - start_time) * 1000

        if elapsed_ms >= self.threshold_ms:
            record = {
                "method": method,
                "url": url,
                "elapsed_ms": round(elapsed_ms, 2),
                "status_code": response.status_code,
            }
            self.slow_requests.append(record)
            logger.warning(
                f"[慢请求] {method} {url} 耗时 {elapsed_ms:.0f}ms "
                f"(阈值: {self.threshold_ms}ms)"
            )

    def on_request_error(self, error, method: str, url: str, **kwargs):
        """请求出错时也清理开始时间记录，避免内存泄漏。"""
        key = f"{method}_{url}"
        self._request_start_times.pop(key, None)

    def after_test(self, test_name: str, result: str):
        """每个测试结束后，如果有慢请求则输出提示。"""
        if self.slow_requests:
            logger.info(
                f"[SlowRequestPlugin] 本次测试包含 {len(self.slow_requests)} 个慢请求"
            )

    def get_report(self) -> str:
        """获取慢请求汇总报告（可在 conftest.py 的 session 级 fixture 中调用）。"""
        if not self.slow_requests:
            return "未发现慢请求"

        lines = [
            f"===== 慢请求报告（阈值: {self.threshold_ms}ms）=====",
            f"共 {len(self.slow_requests)} 个慢请求：",
        ]
        # 按耗时降序排列
        sorted_requests = sorted(
            self.slow_requests, key=lambda r: r["elapsed_ms"], reverse=True
        )
        for i, req in enumerate(sorted_requests, 1):
            lines.append(
                f"  {i}. [{req['status_code']}] {req['method']} {req['url']} "
                f"- {req['elapsed_ms']}ms"
            )
        return "\n".join(lines)
```

## 第六章 熔断器（common/circuit_breaker.py）

### 6.1 熔断器模式的背景

在正常软件开发中，熔断器（Circuit Breaker）通常用于微服务之间的调用保护。但在自动化测试框架中，同样有引入熔断器的必要性。

**测试框架为什么需要熔断器？**

一次典型的接口测试可能需要发起数十甚至数百次 HTTP 请求。当被测服务（如 TakeoutSystem 的 Spring Boot 后端）出现以下情况时，如果没有熔断保护，后果会很严重：

| 场景           | 无熔断保护的问题                                         | 有熔断保护的效果                            |
| -------------- | -------------------------------------------------------- | ------------------------------------------- |
| 后端服务宕机   | 每个请求等待连接超时（默认 30s），100 个用例要等 50 分钟 | 触发熔断后立刻拒绝，节省大量时间            |
| 接口响应极慢   | 测试线程被阻塞，串行执行愈发缓慢                         | 熔断后快速失败，让 CI/CD 流水线早失败早发现 |
| 数据库连接耗尽 | 所有测试都堆积在等待队列，资源浪费                       | 熔断后停止新请求，让后端有机会恢复          |
| 认证服务故障   | 每个需要 token 的用例都重复尝试登录并超时                | 认证熔断器触发后，相关用例立即报错提示熔断  |

核心思想是：**宁可测试失败得快，也不要失败得慢**。快速失败帮助开发者立刻定位问题，而不是在超时日志中大海捞针。

---

### 6.2 三态状态机

熔断器有三种状态，形成一个状态机。理解状态转换是理解熔断器行为的关键。

```
          失败次数 >= failure_threshold
  CLOSED ──────────────────────────────► OPEN
    ▲                                      │
    │                                      │ 等待 timeout 秒后
    │  探测请求成功                          ▼
    └──────────────────────────── HALF_OPEN
                                           │
                                           │ 探测请求失败
                                           ▼
                                         OPEN（重新回到开启）
```

**详细状态说明：**

```
┌─────────────────────────────────────────────────────────────────┐
│  状态       │  含义               │  行为                        │
├─────────────┼─────────────────────┼──────────────────────────────┤
│  CLOSED     │  正常工作（关闭）   │  放行所有请求，统计失败次数   │
│  OPEN       │  熔断中（开启）     │  拒绝所有请求，抛出错误       │
│  HALF_OPEN  │  半开探测           │  放行一个请求，视结果决定走向 │
└─────────────┴─────────────────────┴──────────────────────────────┘
```

**状态转换触发条件：**

- `CLOSED → OPEN`：连续失败次数累计达到 `failure_threshold`（默认 5 次）
- `OPEN → HALF_OPEN`：距离最后一次失败已超过 `timeout` 秒（默认 60 秒），下一个请求到来时自动切换
- `HALF_OPEN → CLOSED`：探测请求执行成功，`_record_success()` 将状态重置为 CLOSED，并清零失败计数
- `HALF_OPEN → OPEN`：探测请求再次失败，`_record_failure()` 重新触发熔断，更新 `last_failure_time`，计时重新开始

这个状态机的设计关键在于：HALF_OPEN 状态下只放行「一个」请求作为探针，如果探针失败，立刻回到 OPEN，**不会继续放行**。这保护了仍然脆弱的后端不被大量并发探测请求再次压垮。

---

### 6.3 CircuitBreaker 类详解

#### 构造参数说明

```python
CircuitBreaker(
    failure_threshold=5,        # 失败阈值：连续失败几次后熔断
    timeout=60,                 # 熔断持续时间（秒）：OPEN 状态保持多久
    expected_exception=Exception,  # 触发熔断的异常类型
    name="default"              # 熔断器名称，用于日志区分
)
```

- `failure_threshold`：累计失败 N 次后触发熔断。设得越小，系统越敏感；设得越大，容错能力越强。测试框架建议设 3~5，不宜过高，否则等待时间太长。
- `timeout`：熔断后等多久才尝试恢复（进入 HALF_OPEN）。建议与被测服务的重启时间对齐，如服务重启需 30 秒则设 30~60。
- `expected_exception`：**只有这个类型的异常才会被计入失败次数**。例如设为 `requests.exceptions.ConnectionError` 时，仅网络错误触发熔断，业务逻辑异常（如断言失败）不会触发。默认是 `Exception`，即所有异常均计入。
- `name`：纯字符串标识，仅用于日志打印，如 `"auth_service"`、`"product_api"` 等，便于在日志中区分多个熔断器的状态。

#### 线程安全设计

`CircuitBreaker` 使用 `threading.Lock()` 保护所有状态读写操作：

```python
self._lock = threading.Lock()
```

在 pytest 并发执行（`pytest-xdist`）场景下，多个测试线程可能同时调用同一个熔断器。`_lock` 确保以下操作的原子性：

- `call()` 方法中检查和切换 OPEN → HALF_OPEN 的判断
- `_record_failure()` 中累加 `self.failures` 和更新 `last_failure_time`
- `_record_success()` 中重置 `self.failures` 和切换 HALF_OPEN → CLOSED
- `get_state()` 和 `get_failures()` 的读取操作

注意一个细节：`call()` 方法先在 `with self._lock` 块内检查状态并可能切换至 HALF_OPEN，然后**释放锁**后才执行实际函数调用。这是刻意的设计——在持有锁的情况下执行可能耗时很久的 HTTP 请求会导致其他线程全部阻塞。

#### \_record_success / \_record_failure 的逻辑

**`_record_success()`** 的关键逻辑：

```python
def _record_success(self):
    with self._lock:
        if self.state == CircuitState.HALF_OPEN:
            # 只有在半开状态下成功，才正式恢复
            self.state = CircuitState.CLOSED
            self.failures = 0
        elif self.state == CircuitState.CLOSED:
            # 正常状态下成功，清零失败计数（避免历史失败影响未来判断）
            self.failures = 0
```

注意：`OPEN` 状态下不会有成功记录，因为 `OPEN` 状态直接抛出 `CircuitBreakerError`，根本不执行函数。

**`_record_failure()`** 的关键逻辑：

```python
def _record_failure(self):
    with self._lock:
        self.failures += 1
        self.last_failure_time = time.time()   # 记录时间，用于计算 timeout

        if self.failures >= self.failure_threshold:
            self.state = CircuitState.OPEN     # 超阈值，立即熔断
```

每次失败都会更新 `last_failure_time`，这意味着 timeout 倒计时从**最后一次失败**开始计算，而不是从第一次失败。这个设计是合理的——如果服务持续失败，我们希望等它稳定下来后再探测。

### 6.4 装饰器用法

`@circuit_breaker` 是最简洁的使用方式，适合在 fixture 或工具函数层面使用：

### 6.6 RetryWithCircuitBreaker

`RetryWithCircuitBreaker` 将重试机制与熔断保护组合在一起，解决了单独使用两者时的冲突问题。

#### 重试与熔断的协作原则

关键规则：**`CircuitBreakerError` 不重试**。

```python
for attempt in range(self.max_retries + 1):
    try:
        if self.circuit_breaker:
            return self.circuit_breaker.call(func, *args, **kwargs)
        else:
            return func(*args, **kwargs)
    except CircuitBreakerError:
        raise   # 直接向上抛出，不进入重试循环
    except Exception as e:
        # 普通异常才重试
        wait_time = self.backoff_factor * (2 ** attempt)
        time.sleep(wait_time)
```

为什么熔断时不重试？因为熔断器开启意味着下游服务已经持续失败多次，此时重试只会：

1. 浪费时间（每次都立刻失败）
2. 可能触发更多的熔断计数（对某些配置而言）
3. 掩盖熔断信号——调用者应该知道是熔断导致的失败，而不是以为是偶发错误

#### 退避算法

指数退避（Exponential Backoff）的公式：

```
wait_time = backoff_factor × 2^attempt
```

具体数值（`backoff_factor=1.0`，`max_retries=3`）：

| 第几次尝试（attempt） | 等待时间计算                 | 实际等待 |
| --------------------- | ---------------------------- | -------- |
| 0（首次尝试失败）     | 1.0 × 2^0 = 1.0s             | 1 秒     |
| 1（第1次重试失败）    | 1.0 × 2^1 = 2.0s             | 2 秒     |
| 2（第2次重试失败）    | 1.0 × 2^2 = 4.0s             | 4 秒     |
| 3（第3次重试失败）    | — 已达最大重试次数，直接抛出 | —        |

随着重试次数增加，等待时间翻倍。这种设计避免了在服务刚恢复时被大量瞬时重试请求再次压垮（雪崩效应）。

**使用示例：**

```python
from common.circuit_breaker import RetryWithCircuitBreaker, CircuitBreaker

# 创建带熔断保护的重试器
cb = CircuitBreaker(failure_threshold=5, timeout=60, name="order_service")
retry = RetryWithCircuitBreaker(
    max_retries=3,
    backoff_factor=0.5,  # 等待 0.5s, 1s, 2s
    circuit_breaker=cb
)

# 执行带重试的调用
result = retry.call(create_order_request, order_data)
```

## 第七章 限流器（common/rate_limiter.py）

### 7.1 为什么需要限流

自动化测试天然具有"高并发、密集请求"的特点。一个测试套件可能在几秒内向同一个接口发送上百个请求，这在生产环境测试或集成测试中会引发两类问题：

**1. 把被测服务打垮（DoS 效果）**

测试框架本质上是在用极高的请求频率访问后端服务。如果被测系统本身有连接池限制（如数据库连接池上限 20 个），密集测试可能导致连接耗尽、服务响应变慢、甚至崩溃。这使得测试结果不可靠——用例失败可能是因为"被测试打垮了"而非真正的 Bug。

**2. 触发被测服务的内置限流**

很多生产系统会对 IP 或账号进行请求频率限制（如：同一 IP 每秒最多 10 次请求）。测试框架如果不限速，会频繁触发 429 Too Many Requests，导致大量测试误判为失败。

**3. 模拟真实用户速率**

性能测试、负载测试场景下，需要模拟真实用户的访问节奏（如：每分钟 100 个用户下单），而不是瞬间打满。限流器提供了精确控制请求速率的能力。

---

### 7.2 三种算法对比

框架实现了三种限流算法，适用于不同场景：

| 维度             | 滑动窗口（RateLimiter）                      | 令牌桶（TokenBucket）              | 漏桶（LeakyBucket）                  |
| ---------------- | -------------------------------------------- | ---------------------------------- | ------------------------------------ |
| **核心数据结构** | 时间戳列表 `calls[]`                         | 浮点数令牌计数 `tokens`            | 浮点数水位 `water_level`             |
| **算法原理**     | 维护窗口内的所有请求时间戳，窗口外的记录丢弃 | 桶以固定速率补充令牌，请求消费令牌 | 桶以固定速率漏水，请求向桶内加水     |
| **突发流量**     | 允许，只要窗口内总量不超限                   | 允许，令牌积累后可突发消耗         | 不允许，超出漏水速率的请求被拒绝     |
| **输出速率**     | 不均匀（可能集中在某时间点）                 | 不均匀（允许突发）                 | 均匀平滑（漏水速率即为最大输出速率） |
| **内存占用**     | 与请求量正相关（存储每个时间戳）             | O(1)（只存一个数字）               | O(1)（只存一个数字）                 |
| **优点**         | 精确统计窗口内请求数，直观                   | 允许适度突发，对用户体验友好       | 输出均匀，对后端最友好               |
| **缺点**         | 在大量请求时，列表清理有开销                 | 令牌积累过多时可能产生较大突发     | 过于严格，可能让合理的短时突发被拒绝 |
| **适用测试场景** | API 并发测试（控制窗口内总次数）             | 模拟真实用户（有突发但有上限）     | 压力测试中的均匀负载施压             |

### 7.3 RateLimiter 详解

`RateLimiter` 使用**滑动窗口**算法，核心思想是：始终只统计"最近 `period` 秒内"的请求次数。

#### 滑动窗口原理

```
时间轴: ──────────────────────────────────────────►
                    │← period（窗口） →│
calls 列表:  [t1, t2, t3, t4, t5]   → 当前时刻
                                     ↑
                           每次调用都清除 now - t > period 的旧记录
```

`calls` 列表存储每次成功请求的时间戳。每次调用 `acquire()` 时：

1. 清理列表中所有超过 `period` 时间的旧记录（它们已经"滑出"窗口）
2. 检查当前窗口内剩余的记录数是否已达 `max_calls`
3. 未达上限则追加当前时间戳并返回 `True`，否则返回 `False`

#### acquire() 方法

```python
def acquire(self) -> bool:
    with self._lock:
        now = time.time()
        # 清理滑出窗口的旧记录
        self.calls = [t for t in self.calls if now - t < self.period]

        if len(self.calls) >= self.max_calls:
            return False      # 窗口已满，拒绝

        self.calls.append(now)
        return True           # 记录本次请求并允许
```

`acquire()` 是非阻塞的——它只返回是否被允许，不等待。适合需要手动处理被限流情况的场景。

#### wait() 方法

```python
def wait(self):
    while not self.acquire():
        oldest_call = self.calls[0]   # 窗口内最早的一条记录
        wait_time = self.period - (time.time() - oldest_call)
        if wait_time > 0:
            time.sleep(wait_time)     # 等到最早的记录滑出窗口
```

`wait()` 是阻塞的。当窗口满时，计算"最早那条记录还需多久滑出窗口"，睡眠这段时间后再重试。这比无限循环 busy-wait 效率高得多。

#### 装饰器用法示例

`RateLimiter` 实例本身可作为装饰器使用（实现了 `__call__`）：

```python
from common.rate_limiter import RateLimiter

# 创建限流器：10 秒内最多 5 次请求
limiter = RateLimiter(max_calls=5, period=10.0)

@limiter
def search_products(keyword):
    """搜索商品接口——自动限流，不会超过 5次/10秒"""
    resp = requests.get(f"/product/search?keyword={keyword}")
    return resp.json()

# 或者在 fixture 中使用 wait()
def call_with_limit(func, *args):
    limiter.wait()   # 阻塞直到获得许可
    return func(*args)
```

装饰器版本的实现（`__call__` 方法）在达到限流时会自动等待并清空记录后继续，无需调用方处理，是最简单的用法。

### 7.4 TokenBucket 详解

#### 令牌补充原理

令牌桶的核心是**懒计算**（Lazy Evaluation）：不用定时器每秒补充令牌，而是在每次 `consume()` 调用时，根据距上次补充的时间差按比例计算应补充多少令牌：

```python
def _refill(self):
    now = time.time()
    elapsed = now - self.last_refill          # 经过了多少秒
    tokens_to_add = elapsed * self.refill_rate  # 按速率计算应补充量

    self.tokens = min(self.capacity, self.tokens + tokens_to_add)  # 不超过桶容量
    self.last_refill = now
```

例如：`capacity=10, refill_rate=2.0`（每秒补充 2 个令牌）：

- 初始时 `tokens=10`（满桶）
- 消费 5 个后 `tokens=5`
- 3 秒后再次调用 `_refill()`：`tokens = min(10, 5 + 3×2) = min(10, 11) = 10`（重新装满）

#### consume() 与 wait_for_token() 的使用场景

```python
# consume()：非阻塞，适合"能做就做，不能做就报告"的场景
bucket = TokenBucket(capacity=10, refill_rate=2.0)

if bucket.consume(1):
    send_api_request()
else:
    logger.warning("令牌不足，跳过本次请求")

# wait_for_token()：阻塞，适合"必须执行，但要控速"的场景
bucket.wait_for_token(1)   # 等到有令牌才继续
send_api_request()
```

令牌桶的突发特性在测试中很有价值：测试开始时桶是满的，可以快速发出多个请求（模拟用户集中操作），之后速率自然降低到 `refill_rate`（模拟稳定使用阶段）。这比固定速率限流更接近真实用户行为。

### 7.5 LeakyBucket 详解

#### 漏桶与令牌桶的本质区别

两种算法都解决限流问题，但出发点相反：

```
令牌桶（TokenBucket）思维：
  "我有多少配额可以用？"
  → 控制的是输入速率上限
  → 允许积累令牌，允许突发
  → 关注调用方

漏桶（LeakyBucket）思维：
  "我能处理多少请求？"
  → 控制的是输出速率
  → 超出容量的请求直接溢出（拒绝），不积压
  → 关注被调用方（后端服务）
```

用水的比喻理解：

```
令牌桶：一个装有令牌的桶，以固定速率往里放令牌，每次请求取走令牌。
        桶满了令牌不再增加，但可以一次取多个（突发）。

漏桶：  一个装水的桶，请求相当于往里灌水，底部有一个固定大小的孔在漏水（处理请求）。
        桶满了新来的水（请求）直接溢出被丢弃，底部漏水速率恒定（输出均匀）。
```

**核心差异总结：**

|          | 令牌桶                         | 漏桶                           |
| -------- | ------------------------------ | ------------------------------ |
| 突发处理 | 允许（积累的令牌可以一次消费） | 不允许（超容量直接拒绝）       |
| 输出节奏 | 不均匀（取决于消费速度）       | 严格均匀（= leak_rate）        |
| 后端压力 | 可能有突发冲击                 | 极其平滑，对后端最友好         |
| 测试用途 | 模拟用户行为（有自然突发）     | 压力测试（给后端施加均匀负载） |

**使用示例：**

```python
from common.rate_limiter import LeakyBucket

# 漏桶：容量 20，每秒处理 5 个请求（即每 0.2 秒一个）
leaky = LeakyBucket(capacity=20, leak_rate=5.0)

def send_order_request(order_data):
    if leaky.add(1):        # 尝试向桶里加水
        return do_request(order_data)
    else:
        raise Exception("请求被限流丢弃")    # 桶满了

# 或者等待有空间
leaky.wait_for_space(1)     # 阻塞直到桶有空间
do_request(order_data)
```

## 第八章 安全模块（common/security.py）

### 8.1 SensitiveDataFilter

`SensitiveDataFilter` 继承自 `logging.Filter`，以**日志过滤器**的形式工作。它不主动脱敏，而是被动地拦截每一条日志记录，在记录被写入之前替换掉其中的敏感信息。

#### 监听的敏感字段

```python
SENSITIVE_FIELDS = [
    'password',      # 密码（最常见）
    'passwd',        # 密码别名
    'pwd',           # 密码缩写
    'secret',        # 秘钥/密文
    'token',         # 访问令牌
    'apikey',        # API 密钥（无下划线形式）
    'api_key',       # API 密钥（有下划线形式）
    'authorization', # HTTP Authorization 头
    'auth',          # 认证信息
    'credential',    # 凭证
    'credit_card'    # 信用卡号
]
```

这 11 个字段覆盖了测试过程中最常见的敏感信息类型。匹配时大小写不敏感（`re.IGNORECASE`）。

#### 三类正则模式

**模式一：JSON 字段匹配**

针对日志中打印的 JSON 请求体或响应体：

```python
# 模式：字段名 + 分隔符 + 值
pattern = re.compile(
    r'(' + field + r'["\s]*[:=]["\s]*)([^",}\s]+)',
    re.IGNORECASE
)
```

匹配示例：

```
原始日志：{"username": "alice", "password": "secret123", "phone": "138..."}
过滤结果：{"username": "alice", "password": "***", "phone": "138..."}

原始日志：password = "mypassword"
过滤结果：password = "***"
```

**模式二：URL 参数匹配**

针对日志中打印的完整请求 URL：

```python
url_pattern = re.compile(
    r'(' + '|'.join(SENSITIVE_FIELDS) + r')=[^&\s]+',
    re.IGNORECASE
)
```

匹配示例：

```
原始日志：GET /api/login?username=alice&password=secret123&redirect=/home
过滤结果：GET /api/login?username=alice&password=***&redirect=/home
```

**模式三：Bearer Token 匹配**

针对日志中打印的 HTTP 请求头：

```python
bearer_pattern = re.compile(r'(Bearer\s+)[A-Za-z0-9\-._~+/]+=*', re.IGNORECASE)
```

匹配示例：

```
原始日志：Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0...
过滤结果：Authorization: Bearer ***
```

注意正则中的字符集 `[A-Za-z0-9\-._~+/]+=*` 专门针对 Base64URL 编码的 JWT Token（允许 `.` 分隔符、可选的 `=` 填充）。

#### filter() 方法的工作原理

```python
def filter(self, record: logging.LogRecord) -> bool:
    if record.msg:
        record.msg = self._sanitize_data(str(record.msg))   # 过滤主消息

    if hasattr(record, 'args') and record.args:
        new_args = []
        for arg in record.args:
            if isinstance(arg, (dict, str)):
                new_args.append(self._sanitize_data(str(arg)))  # 过滤 % 格式化的参数
            else:
                new_args.append(arg)
        record.args = tuple(new_args)

    return True   # 永远返回 True：只修改内容，不丢弃日志记录
```

`filter()` 方法的返回值为 `True` 意味着**所有日志都会被保留**，只是内容中的敏感信息被替换为 `***`。这是关键：日志不能因为包含敏感信息就被整条删除（那样会让故障排查更困难），正确做法是脱敏后保留。

另外，`record.args` 是 Python logging 中 `%`-style 格式化的参数（如 `logger.info("user %s login", username)`），代码对此也做了处理，确保不会因为格式化参数中包含敏感信息而泄露。

#### 在 conftest.py 中的初始化位置

应在**最高层**的 `conftest.py`（项目根目录）中，在 session 级别的 fixture 里初始化，确保所有测试的日志都经过过滤：

```python
# conftest.py（项目根目录）
import logging
from common.security import setup_sensitive_data_filter

# 方式一：给根 logger 添加过滤器（影响所有日志）
setup_sensitive_data_filter(logging.getLogger())

# 方式二：给框架专用 logger 添加过滤器
setup_sensitive_data_filter(logging.getLogger("tests"))
setup_sensitive_data_filter(logging.getLogger("common"))
```

应在 `conftest.py` 模块级别（而非 fixture 内部）执行，确保 pytest 收集测试阶段就已生效，而不是等到第一个 fixture 被调用时才生效。

### 8.2 DataMasker

`DataMasker` 是主动脱敏工具，不依赖日志系统，适合在生成测试报告、打印调试信息、或构造展示用数据时手动调用。

#### 四种脱敏方法的规则与示例

**mask_password()**

```python
DataMasker.mask_password("secret123")             # → "***"        （visible_chars=0，完全隐藏）
DataMasker.mask_password("secret123", visible_chars=2)  # → "se*******"  （保留前2个字符）
DataMasker.mask_password("ab", visible_chars=2)   # → "a*"         （密码比 visible_chars 短时，只保留1个）
DataMasker.mask_password("")                       # → "***"        （空值保护）
```

规则：当 `visible_chars <= 0` 时完全替换为 `***`；当密码长度 <= `visible_chars` 时，只保留第一个字符，其余全部遮盖（防止短密码被完整暴露）。

**mask_email()**

```python
DataMasker.mask_email("user@example.com")     # → "u**r@e******.com"
DataMasker.mask_email("alice@gmail.com")      # → "a***e@g****.com"
DataMasker.mask_email("ab@test.org")          # → "**@t***.org"     （本地部分 <= 2 字符时全遮盖）
DataMasker.mask_email("invalid-email")        # → "***@***.***"     （无 @ 时返回固定替换）
```

规则：

- 本地部分（`@` 前）：长度 > 2 时保留首尾各 1 个字符，中间全遮盖；否则全遮盖
- 域名部分：只保留域名首字母和顶级域（`.com`、`.org` 等），其余遮盖

**mask_phone()**

```python
DataMasker.mask_phone("13800000003")    # → "138****003"
DataMasker.mask_phone("021-1234-5678")  # → "021****678"    （自动剥离非数字字符）
DataMasker.mask_phone("1234")           # → "****"          （短号码全遮盖）
DataMasker.mask_phone("")              # → "***"
```

规则：提取纯数字后，保留前 3 位和后 3 位，中间全遮盖。手机号（11 位）显示为 `138****003`，座机号（10~11 位含区号）同样适用。

**mask_credit_card()**

```python
DataMasker.mask_credit_card("4111111111111111")  # → "************1111"
DataMasker.mask_credit_card("4111-1111-1111-1111")  # → "************1111"  （剥离横线）
DataMasker.mask_credit_card("1234")              # → "****"              （短于4位全遮盖）
DataMasker.mask_credit_card("")                 # → "**** **** **** ****"
```

规则：提取纯数字后，只保留最后 4 位（银行卡末 4 位是常见的身份确认方式，保留有合理性），其余全部遮盖。

#### mask_dict() 的批量脱敏用法

`mask_dict()` 遍历字典的所有键，对键名中包含敏感词的字段进行脱敏：

```python
from common.security import DataMasker

# 场景：在测试报告中展示请求参数时，对敏感字段脱敏
request_data = {
    "phone": "13800000001",
    "password": "testpassword",
    "username": "alice",
    "token": "eyJhbGci...",
    "amount": 99.9
}

safe_data = DataMasker.mask_dict(request_data)
# 结果：
# {
#   "phone": "138****001",    ← 含 'phone'，调用 mask_phone()
#   "password": "***",        ← 含 'password'，调用 mask_password()
#   "username": "alice",      ← 不含敏感词，原样保留
#   "token": "***",           ← 含 'token'，通用遮盖
#   "amount": 99.9            ← 非字符串，原样保留
# }

# 自定义敏感字段列表
safe_data = DataMasker.mask_dict(request_data, sensitive_keys=['password', 'token'])
```

`mask_dict()` 的键名匹配逻辑（`any(sensitive in key.lower() for sensitive in sensitive_keys)`）使用**包含匹配**而非精确匹配，因此 `user_password`、`old_password` 等复合键名也会被正确识别。

### 9.1 YamlUtil

`YamlUtil` 是对 PyYAML 库的薄封装，提供三个静态方法用于 YAML 文件的读写和嵌套值访问。

#### load_yaml / save_yaml

```python
# load_yaml：带文件存在性检查，空文件返回空字典而非 None
data = YamlUtil.load_yaml("data/api_test_data.yaml")

# 使用 yaml.safe_load（不是 yaml.load）——安全加载，防止任意代码执行
# 若文件为空或只有注释，safe_load 返回 None，代码中转换为 {} 确保调用方可直接遍历
```

```python
# save_yaml：自动创建目录，以 UTF-8 编码保存，allow_unicode=True 支持中文
YamlUtil.save_yaml({"key": "值"}, "output/result.yaml")
# → 自动执行 os.makedirs(os.path.dirname(file_path), exist_ok=True)
```

`save_yaml` 的 `allow_unicode=True` 参数非常重要——默认情况下 PyYAML 会将中文字符序列化为 `\uXXXX` 转义形式，设置此参数后中文原样保存，便于人工阅读测试结果文件。

#### get_value() 的点路径访问

`get_value()` 通过 `.` 分隔的路径字符串访问嵌套字典，避免繁琐的多层 `dict.get()` 链式调用：

```python
# 假设 data/api_test_data.yaml 内容如下：
# auth:
#   valid_accounts:
#     - phone: "13800000001"
#       password: "password123"
#       role: "user"
#   invalid_accounts:
#     - phone: "00000000000"

data = YamlUtil.load_yaml("data/api_test_data.yaml")

# 方式一：传统多层访问（繁琐，每层都可能 KeyError 或 None）
account = data.get("auth", {}).get("valid_accounts", [{}])[0].get("phone")

# 方式二：get_value() 点路径访问（简洁，中间任意层缺失时返回 None）
phone = YamlUtil.get_value(data, "auth.valid_accounts")   # 返回整个列表
```

注意：`get_value()` 只支持字符串 key 的字典层级访问，**不支持列表下标**（如 `"auth.valid_accounts.0.phone"` 中的 `0` 会因为 `result.get("0")` 返回 `None` 而失败）。访问列表元素需要先获取列表后用下标：

```python
accounts = YamlUtil.get_value(data, "auth.valid_accounts")
first_phone = accounts[0]["phone"] if accounts else None
```

### 9.2 DataHelper 数据加载器

`DataHelper` 是框架中测试数据的**统一入口**，基于类变量实现内存缓存，对外提供按业务模块划分的数据访问接口。

#### 缓存机制：为什么要缓存

YAML 文件的 I/O 读取和解析在单次调用时耗时不多（通常几毫秒），但在大型测试套件中的影响不可忽视：

```
假设：api_test_data.yaml 大小 50KB，解析耗时 5ms
套件规模：300 个测试用例，每个用例调用 3 次 get_auth_data()
无缓存总耗时：300 × 3 × 5ms = 4500ms = 4.5 秒 纯文件 I/O
有缓存总耗时：1 × 5ms = 5ms（只在首次加载时读文件）
```

缓存实现：

```python
_data_cache: Dict[str, Dict] = {}   # 类变量，所有实例共享（实际上这是个只用类方法的工具类）

@classmethod
def load_api_data(cls) -> dict:
    if 'api' not in cls._data_cache:   # 首次调用时加载
        file_path = os.path.join(cls.get_data_dir(), 'api_test_data.yaml')
        cls._data_cache['api'] = YamlUtil.load_yaml(file_path)
    return cls._data_cache['api']      # 后续调用直接从内存返回
```

由于 `_data_cache` 是类变量，在一个 pytest session 内只要不调用 `clear_cache()`，文件只会被读取**一次**。

#### 各 get_xxx_data() 方法返回的内容概述

所有方法都从两个 YAML 文件切片，返回对应业务模块的字典：

**来自 `data/api_test_data.yaml`（API 层测试数据）：**

| 方法                  | YAML 节点   | 典型内容                            |
| --------------------- | ----------- | ----------------------------------- |
| `get_auth_data()`     | `auth:`     | 有效/无效账号列表、登录测试用例参数 |
| `get_merchant_data()` | `merchant:` | 商家注册、商家信息、门店数据        |
| `get_product_data()`  | `product:`  | 商品列表、商品详情、分类数据        |
| `get_cart_data()`     | `cart:`     | 购物车增删改查的测试参数            |
| `get_order_data()`    | `order:`    | 下单、取消、查询订单的测试数据      |
| `get_review_data()`   | `review:`   | 评价内容、评分等级测试数据          |
| `get_boundary_data()` | `boundary:` | 边界值（最大/最小长度、特殊字符等） |
| `get_security_data()` | `security:` | SQL 注入、XSS 攻击、异常参数等      |

**来自 `data/web_test_data.yaml`（UI 层测试数据）：**

| 方法                      | YAML 节点       | 典型内容                      |
| ------------------------- | --------------- | ----------------------------- |
| `get_h5_web_data()`       | `h5:`           | H5 用户端的 Selenium 测试数据 |
| `get_merchant_web_data()` | `merchant_web:` | 商家端后台的 UI 测试数据      |
| `get_admin_web_data()`    | `admin_web:`    | 管理后台的 UI 测试数据        |

#### clear_cache() 的使用场景

`clear_cache()` 清空类变量 `_data_cache`，强制下次访问时重新从磁盘读取：

```python
# 场景一：测试隔离——某个测试修改了 YAML 文件内容后，需要让后续测试看到更新
def test_with_dynamic_data():
    # 动态写入测试数据
    YamlUtil.save_yaml(new_data, "data/api_test_data.yaml")
    DataHelper.clear_cache()   # 清除旧缓存

    fresh_data = DataHelper.get_auth_data()   # 读到新写入的数据

# 场景二：参数化测试与数据更新的配合
@pytest.fixture(autouse=True)
def reset_data_cache():
    yield
    DataHelper.clear_cache()   # 每个测试结束后清空缓存，确保数据隔离

# 场景三：在不同测试阶段使用不同的数据文件（通过修改 _data_dir）
DataHelper._data_dir = "/path/to/staging/data"
DataHelper.clear_cache()   # 切换数据目录后必须清除缓存
```

注意：大多数情况下**不需要**调用 `clear_cache()`，因为测试数据文件在测试运行期间通常是只读的。只有在测试本身会修改 YAML 文件（动态数据生成测试）或需要在同一进程中切换数据源时才需要使用。

### 9.3 数据与测试解耦的意义

将测试数据放在 YAML 文件而非硬编码在测试代码中，是测试框架设计的核心原则之一。

#### 对比两种方式的实际差异

**硬编码方式（不推荐）：**

```python
# tests/test_auth.py
def test_login():
    resp = client.post("/user/login", json={
        "phone": "13800000001",   # 硬编码！
        "password": "password123"  # 硬编码！
    })
    assert resp.status_code == 200
```

问题：

- 需要更换测试账号时，要修改所有测试文件（散布在几十个文件里）
- 密码等敏感数据直接暴露在代码中，进入版本控制系统
- 非技术人员（测试工程师、QA）无法独立维护测试数据
- 同一份数据（如有效账号）在多个测试文件中重复定义，修改时容易遗漏

**YAML 外置方式（推荐）：**

```python
# tests/test_auth.py
def test_login():
    auth_data = DataHelper.get_auth_data()
    account = auth_data["valid_accounts"][0]  # 从 YAML 读取

    resp = client.post("/user/login", json={
        "phone": account["phone"],
        "password": account["password"]
    })
    assert resp.status_code == 200
```

```yaml
# data/api_test_data.yaml
auth:
  valid_accounts:
    - phone: "13800000001"
      password: "password123"
      role: "user"
```

#### 解耦带来的具体好处

1. **单点维护**：测试账号、环境参数只需在 YAML 中修改一处，所有引用该数据的测试自动生效

2. **环境切换简单**：通过替换或切换 YAML 文件，可以让同一套测试代码对应开发、测试、预发布多个环境的数据，而无需修改任何测试代码

3. **安全性提升**：可以将 YAML 数据文件排除在 Git 追踪之外（`.gitignore`），或使用加密工具管理，而测试代码本身则可以安全地提交

4. **可读性强**：YAML 格式对非开发人员友好，QA 工程师可以直接阅读和编辑测试数据，不需要理解 Python 代码

5. **参数化测试天然支持**：YAML 中的列表结构与 pytest 的 `@pytest.mark.parametrize` 配合非常自然，数据增减不影响测试代码逻辑：

```python
@pytest.mark.parametrize("account", DataHelper.get_auth_data()["valid_accounts"])
def test_all_valid_accounts_can_login(account):
    resp = client.post("/user/login", json=account)
    assert resp.status_code == 200
# YAML 中新增一个账号 → 自动多跑一个测试用例，零代码改动
```

6. **测试数据版本化**：数据文件独立于代码文件，可以单独进行版本管理，方便追踪"测试在哪个版本开始使用了哪批数据"

## 第十章 API 封装层（api/）

### 10.1 设计理念

#### 10.1.1 为什么需要 BaseApi

在自动化测试中，直接在测试用例里调用 `requests.get(...)` 会带来几个问题：

1. **重复代码**：每个测试都要拼 URL、设置 headers、处理超时，代码大量重复。
2. **维护困难**：API 端点变更时，需要修改所有引用该端点的测试用例。
3. **无可观测性**：没有统一的日志记录，定位失败原因困难。
4. **无法集成基础设施**：熔断器、限流器、重试策略这些企业级能力无处挂载。

`BaseApi` 解决了这些问题。它是所有业务 API 类的父类，提供统一的 HTTP 方法封装（GET/POST/PUT/DELETE）、日志记录和 Allure 步骤集成。每个业务模块对应一个继承自 `BaseApi` 的子类，子类只需要定义方法名和端点路径，通用逻辑由父类统一处理。

#### 10.1.2 层级结构

```
测试用例 (test_cases/)
    │
    ▼
业务 API 类 (api/takeout_api.py)   ← 本章重点
    │  AuthApi / UserApi / OrderApi / ...
    ▼
BaseApi (api/base_api.py)          ← 通用 HTTP + 日志 + Allure
    │
    ▼
BaseRequests (common/base_requests.py)  ← 插件系统 + 重试 + Session
    │
    ▼
requests.Session                   ← Python 标准 HTTP 库
```

整个链路中：

- `BaseRequests` 负责底层 HTTP 通信和插件系统（熔断器、限流器、缓存）。
- `BaseApi` 在 `BaseRequests` 之上增加业务层日志和 Allure 步骤装饰。
- 业务 API 子类（如 `OrderApi`）只封装端点路径和参数，不关心传输层细节。

#### 10.1.3 API Object 模式类比 Page Object 模式

`Page Object` 模式是 UI 测试的经典模式：把每个页面的操作封装成一个类，测试用例只调用高层方法（如 `login_page.login("13800138000", "1234")`），不直接操作 DOM 选择器。

`API Object` 模式是相同思路在接口测试上的应用：

| 维度     | Page Object               | API Object               |
| -------- | ------------------------- | ------------------------ |
| 封装对象 | 页面元素与交互            | API 端点与请求参数       |
| 基类     | `BasePage`                | `BaseApi`                |
| 子类示例 | `H5LoginPage`             | `AuthApi`                |
| 测试调用 | `page.login(phone, code)` | `api.login(phone, code)` |
| 隐藏细节 | CSS 选择器、等待条件      | URL路径、JSON字段名      |
| 变更影响 | 只改 Page Object 类       | 只改 API 类              |

当后端把 `/api/auth/login` 改为 `/api/v2/auth/login` 时，只需修改 `AuthApi.login()` 里的路径，所有调用该方法的测试用例无需改动。

#### 10.1.4 `@allure.step` 装饰器的作用

`BaseApi` 的每个 HTTP 方法都使用了 `@allure.step` 装饰器：

```python
@allure.step("GET 请求: {url}")
def get(self, url: str, **kwargs):
    ...
```

作用：在 Allure 报告的 **Steps** 面板中，为每次 HTTP 调用生成一条可展开的步骤记录，显示请求方法和 URL。测试用例调用链越深，步骤树越详细，便于定位失败发生在哪一层。业务 API 子类的方法本身也可以加 `@allure.step`，形成两层步骤树（业务操作 → HTTP 请求）。

### 10.2 BaseApi 详解

**文件路径：** `api/base_api.py`

#### 10.2.1 构造方法

```python
def __init__(self, base_url: str, timeout: int = 30, enable_plugins: bool = True):
    self.base_url = base_url
    self.timeout = timeout
    self.requests = BaseRequests(base_url=base_url, enable_plugins=enable_plugins)
```

三个核心点：

1. **`base_url`**：存储在实例上，用于日志拼接完整 URL。实际 HTTP 请求的 URL 拼接由 `BaseRequests` 完成。
2. **`self.requests`**：持有一个 `BaseRequests` 实例。`BaseRequests` 内部维护 `requests.Session`，同一个 `BaseApi` 实例的所有请求共享同一个 Session，这意味着 `session.headers`（如 Authorization）一经设置，该实例的后续请求都会携带，无需每次传参。
3. **`enable_plugins`**：透传给 `BaseRequests`，控制是否加载插件系统（熔断器、限流器等企业级中间件）。默认开启。

#### 10.2.2 请求日志方法

| 方法                                  | 日志级别 | 记录内容             |
| ------------------------------------- | -------- | -------------------- |
| `_log_request(method, url, **kwargs)` | INFO     | HTTP 方法 + 完整 URL |
| `_log_request`（有 `json` 时追加）    | DEBUG    | 请求体（完整 JSON）  |
| `_log_response(response)`             | INFO     | HTTP 响应状态码      |
| `_log_response`（有响应文本时）       | DEBUG    | 响应体前 500 字符    |

响应体截断到 500 字符的设计是为了防止大响应体（如商品列表）将日志文件撑爆。完整响应体在需要时可通过断言失败信息查看。

`_log_response` 内部用 `try/except` 包裹 `response.text` 读取，防止网络异常或编码问题导致日志方法本身抛出异常，从而屏蔽真正的业务错误。

#### 10.2.3 HTTP 方法封装

四个方法（GET/POST/PUT/DELETE）结构相同，以 `get` 为例：

```python
@allure.step("GET 请求: {url}")
def get(self, url: str, **kwargs) -> Dict[str, Any]:
    self._log_request("GET", f"{self.base_url}{url}")
    response = self.requests.get(url, **kwargs)
    self._log_response(response)
    return response
```

设计要点：

- **返回原始 `response` 对象**，不做任何断言。是否成功由调用方决定，保持方法的单一职责。
- **`**kwargs`透传**：params、headers、files 等参数全部透传给底层`BaseRequests`，`BaseApi` 不限制可以传什么。
- `post` 和 `put` 额外接收 `json_data` 参数（非 `json`，避免与内置关键字冲突），并在内部作为 `json=json_data` 传给底层。

**`close()` 方法：**

```python
def close(self):
    if hasattr(self.requests, 'close'):
        self.requests.close()
```

关闭底层 `requests.Session`，释放连接池资源。通常在测试 fixture 的 teardown 阶段调用，或直接使用 `with` 语句（若子类实现了上下文管理器）。

### 10.3 两个核心工具函数

这两个模块级函数定义在 `api/takeout_api.py` 顶部，不属于任何类，可以直接 `from api.takeout_api import is_success, get_biz_code` 使用。

#### 10.3.1 `is_success(response) -> bool`

**功能：** 判断一次 API 调用是否业务成功。

**判断逻辑（双重条件，缺一不可）：**

1. HTTP 状态码必须是 `200` 或 `201`
2. 响应体 JSON 中的 `success` 字段必须严格等于 `True`（使用 `is True`，而非 `== True`）

```python
def is_success(response) -> bool:
    if response.status_code not in (200, 201):
        return False
    try:
        body = response.json()
        return body.get("success") is True  # 无默认值：缺字段视为失败
    except Exception:
        return False
```

**各场景返回值：**

| HTTP 状态码 | body.success 字段              | `is_success()` 返回 | 说明                                                          |
| ----------- | ------------------------------ | ------------------- | ------------------------------------------------------------- |
| 200         | `True`                         | `True`              | 正常成功                                                      |
| 201         | `True`                         | `True`              | 创建成功（兼容 201）                                          |
| 200         | `False`                        | `False`             | 业务失败（如账号不存在）                                      |
| 200         | 字段不存在（缺 `success` key） | `False`             | `get()` 无默认值，返回 `None`，`None is True` 为 `False`      |
| 400         | 任意                           | `False`             | HTTP 错误，直接短路                                           |
| 500         | `True`                         | `False`             | HTTP 状态码优先，即使服务端错误填了 `success:true` 也不算成功 |
| 200         | JSON 解析失败                  | `False`             | `except Exception` 捕获，视为失败                             |

**关键设计决策——`body.get("success") is True` 而非 `body.get("success", False)`：**

使用无默认值的 `get("success")` 是有意为之的严格设计。如果响应体中缺少 `success` 字段，说明该接口的响应格式不符合约定（TakeoutSystem 所有接口均应返回统一响应体 `{success, code, message, data}`）。此时应当返回 `False`，而不是给一个默认值掩盖格式不一致的问题。

#### 10.3.2 `get_biz_code(response) -> int`

**功能：** 提取响应中的业务状态码（区别于 HTTP 状态码）。

```python
def get_biz_code(response) -> int:
    try:
        return response.json().get("code", response.status_code)
    except Exception:
        return response.status_code
```

TakeoutSystem 使用统一响应体，`code` 字段承载业务含义，例如：

- `200`：成功
- `40001`：手机号格式错误
- `40101`：Token 过期
- `40301`：无权限

`fallback` 到 HTTP 状态码的意义：如果 JSON 解析失败（如服务端崩溃返回 HTML 错误页），或响应体中没有 `code` 字段（如代理层返回的 502），仍然能返回一个有意义的整数，而不是抛出异常。

**典型用法：**

```python
response = auth_api.login("13800138000", "wrong_code")
assert not is_success(response)
assert get_biz_code(response) == 40002  # 验证码错误的业务码
```

### 10.5 Token 注入机制

#### 10.5.1 为什么在 `__init__` 中注入 Token

除 `AuthApi` 和 `HealthApi` 外，其余9个业务 API 类的构造方法都有如下模式：

```python
def __init__(self, token: str = ""):
    super().__init__(base_url=config.API_BASE_URL)
    if token:
        self.requests.session.headers.update({"Authorization": f"Bearer {token}"})
```

**每次请求传 header vs 构造时注入 Session header 的对比：**

| 维度       | 每次请求传 header                                             | 构造时注入 Session               |
| ---------- | ------------------------------------------------------------- | -------------------------------- |
| 代码量     | 每个方法都要传 `headers={"Authorization": f"Bearer {token}"}` | 只在 `__init__` 写一次           |
| 遗漏风险   | 某个方法忘记传 header，静默失败，难以排查                     | 一次设置，该实例所有请求自动携带 |
| 多请求场景 | 10个方法需要传10次                                            | 0次额外操作                      |
| Token 更换 | 麻烦，需要在调用层管理                                        | 创建新的 API 实例即可            |

**Session 级 header 注入** 的本质是利用 `requests.Session` 的 header 持久化机制：设置 `session.headers` 后，该 session 发出的所有请求都会自动附带这些 header，无需在每个请求方法中重复传递。

#### 10.5.2 实际使用模式

**Fixture 层获取 Token 后创建 API 实例：**

```python
@pytest.fixture(scope="module")
def user_api():
    auth = AuthApi()
    auth.send_sms("13800138001")
    resp = auth.login("13800138001", "1234")
    token = resp.json()["data"]["accessToken"]
    return UserApi(token=token)   # Token 在构造时注入
```

之后测试用例直接使用 `user_api.get_profile()`，无需关心 Token。

**多角色场景（用户 + 商家同时操作）：**

```python
user_order_api = OrderApi(token=user_token)     # 用户视角
merchant_order_api = OrderApi(token=merchant_token)  # 商家视角
```

两个 `OrderApi` 实例持有各自的 Session 和 Token，互不干扰，可以在同一个测试用例中协作使用（如：用户下单 → 商家接单 → 用户确认收货的完整流程测试）。

### 11.1 Page Object 设计模式

#### 11.1.1 为什么要用 Page Object

如果测试用例直接操作 DOM：

```python
# 不使用 Page Object 的反例
def test_login():
    driver.find_element(By.CSS_SELECTOR, "input[placeholder='请输入手机号']").send_keys("13800138000")
    driver.find_element(By.CSS_SELECTOR, "button.sms-btn").click()
    driver.find_element(By.CSS_SELECTOR, "input[placeholder='请输入验证码']").send_keys("1234")
    driver.find_element(By.CSS_SELECTOR, "button.login-btn").click()
    assert "/login" not in driver.current_url
```

问题：

1. 选择器散落在测试代码中，Vue 组件改了 class 名，所有测试全挂。
2. 同样的登录操作在10个测试中重复写了10遍。
3. 测试逻辑（"登录然后验证跳转"）被页面细节（"找到这个 CSS 元素"）掩盖。

使用 Page Object 后：

```python
# 使用 Page Object 的正例
def test_login(mobile_driver):
    page = H5LoginPage(mobile_driver).open()
    page.login("13800138000", "1234")
    assert page.is_logged_in()
```

选择器只在 `H5LoginPage` 中维护，测试用例读起来像业务描述。

### 11.2 BasePage 详解

**文件路径：** `page_objects/base_page.py`

#### 11.2.1 构造方法

```python
def __init__(self, driver, timeout=10):
    self.driver = driver
    self.timeout = timeout
    self.wait = WebDriverWait(driver, timeout)
```

- `driver`：Selenium WebDriver 实例（Chrome），由 conftest.py 中的 fixture 创建并注入。
- `timeout`：默认等待超时时间 10 秒。大多数方法内部使用这个值，也允许单次调用时覆盖。
- `self.wait`：预建的 `WebDriverWait` 实例，避免每次调用都重新创建对象。

**注意：** `WebDriverWait` 使用**显式等待**，不依赖 `implicitly_wait`。实际上 conftest.py 中 `d.implicitly_wait(0)` 已关闭隐式等待，强制使用显式等待，这样等待条件更精确，不会产生隐性延迟叠加。

#### 11.2.2 所有方法一览

| 方法                                           | 参数                      | 等待条件                           | 返回值           | 用途                                           |
| ---------------------------------------------- | ------------------------- | ---------------------------------- | ---------------- | ---------------------------------------------- |
| `open(url)`                                    | URL 字符串                | 无（立即跳转）                     | 无               | 导航到指定 URL                                 |
| `find_element(locator)`                        | `(By.XXX, value)` 元组    | `presence_of_element_located`      | WebElement       | 等待并返回单个元素（DOM 存在即可，不要求可见） |
| `find_elements(locator)`                       | `(By.XXX, value)` 元组    | `presence_of_all_elements_located` | List[WebElement] | 等待并返回所有匹配元素                         |
| `click(locator)`                               | `(By.XXX, value)` 元组    | `element_to_be_clickable`          | 无               | 等待可点击后点击（比 `find_element` 更严格）   |
| `input_text(locator, text)`                    | locator + 文本            | `presence_of_element_located`      | 无               | 清空输入框后输入文本                           |
| `get_text(locator)`                            | `(By.XXX, value)` 元组    | `presence_of_element_located`      | str              | 获取元素的可见文本                             |
| `is_element_visible(locator, timeout)`         | locator + 可选超时        | `visibility_of_element_located`    | bool             | 检查元素是否可见，不抛异常（适合条件判断）     |
| `wait_for_element(locator, timeout)`           | locator + 可选超时        | `visibility_of_element_located`    | WebElement       | 等待元素可见并返回（超时则抛异常）             |
| `wait_for_element_disappear(locator, timeout)` | locator + 可选超时        | `invisibility_of_element_located`  | bool             | 等待元素消失（如 loading 动画）                |
| `get_title()`                                  | 无                        | 无                                 | str              | 获取页面 `<title>`                             |
| `get_url()`                                    | 无                        | 无                                 | str              | 获取当前 URL                                   |
| `screenshot(name)`                             | 截图名称前缀              | 无                                 | str（文件路径）  | 保存截图到 `screenshots/` 目录                 |
| `wait_for_url_not_contains(path, timeout)`     | 路径片段 + 超时（默认8s） | lambda 自定义                      | 无               | 等待 URL 不再包含指定片段                      |
| `execute_script(script, *args)`                | JS 代码 + 参数            | 无                                 | Any              | 执行 JavaScript                                |
| `scroll_to_element(locator)`                   | `(By.XXX, value)` 元组    | `presence_of_element_located`      | 无               | 滚动使元素进入视口（`scrollIntoView`）         |
| `hover(locator)`                               | `(By.XXX, value)` 元组    | `presence_of_element_located`      | 无               | 鼠标悬停（触发 hover 样式/下拉菜单）           |

#### 11.2.3 显式等待策略详解

Selenium 的等待有三种：

1. **`time.sleep()`**：固定等待，浪费时间，不推荐。
2. **隐式等待（`implicitly_wait`）**：全局等待，与显式等待混用会产生意外叠加，本框架已关闭。
3. **显式等待（`WebDriverWait` + `expected_conditions`）**：精确等待特定条件，本框架唯一使用的方式。

`BasePage` 中使用了多种 `expected_conditions`（EC）：

| EC 条件                            | 含义                                     | 使用场景                                        |
| ---------------------------------- | ---------------------------------------- | ----------------------------------------------- |
| `presence_of_element_located`      | DOM 中存在该元素（不要求可见）           | `find_element`：查找可能被 CSS 隐藏的元素       |
| `presence_of_all_elements_located` | DOM 中存在所有匹配元素                   | `find_elements`：等待列表加载                   |
| `element_to_be_clickable`          | 元素可见且不被禁用                       | `click`：防止点击到禁用按钮                     |
| `visibility_of_element_located`    | 元素可见（display 不为 none，尺寸不为0） | `wait_for_element`：等待弹窗出现                |
| `invisibility_of_element_located`  | 元素不可见或不存在                       | `wait_for_element_disappear`：等待 loading 消失 |

#### 11.2.4 `wait_for_url_not_contains` 的特殊用途

```python
def wait_for_url_not_contains(self, path: str, timeout: int = 8):
    WebDriverWait(self.driver, timeout).until(
        lambda d: path not in d.current_url
    )
```

Vue3 SPA（单页应用）的路由跳转是纯 JavaScript 操作，不会触发页面刷新，也不会产生新的 HTTP 请求。普通的 `find_element` 只能等待 DOM 元素，无法感知路由变化。

`wait_for_url_not_contains("/login")` 专门用于等待"登录成功跳转"：在用户点击登录按钮后，等待 URL 中不再包含 `/login`，确认路由已跳转到首页或仪表盘。

**典型用法：**

```python
def login(self, phone: str, code: str):
    self.input_text(self.PHONE_INPUT, phone)
    self.click(self.SEND_CODE_BTN)
    self.input_text(self.CODE_INPUT, code)
    self.click(self.SUBMIT_BTN)
    self.wait_for_url_not_contains("/login")  # 等待路由跳转完成
```

#### 11.2.5 `screenshot` 的命名规则

```python
def screenshot(self, name="screenshot"):
    timestamp = time.strftime("%Y%m%d_%H%M%S")
    filename = f"screenshots/{name}_{timestamp}.png"
    os.makedirs("screenshots", exist_ok=True)
    self.driver.save_screenshot(filename)
    return filename
```

生成路径格式：`screenshots/{name}_{YYYYMMDD_HHMMSS}.png`

例如：`screenshots/login_failed_20250630_143022.png`

`os.makedirs("screenshots", exist_ok=True)` 确保目录不存在时自动创建，不会因目录不存在而导致截图失败。截图通常配合 `@pytest.hookimpl` 的失败钩子自动触发，或在关键步骤手动调用用于调试。

### 11.3 三端框架选型与选择器差异

TakeoutSystem 的三端 Web 界面使用了不同的组件库，导致相同功能的 DOM 结构有显著差异：

| 维度         | H5（Vant 4）                                                               | 商家端 / 管理后台（Element Plus）                                                         |
| ------------ | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 适用场景     | 手机浏览器（移动端）                                                       | 桌面浏览器                                                                                |
| 输入框选择器 | `input[placeholder='...']`（Vant 直接渲染 `<input>`）                      | `input[placeholder='...']` 或 `.el-input__inner`（Element Plus 2.x 已改为直接 `<input>`） |
| 按钮选择器   | `.van-button`、`.login-btn`（自定义 class）                                | `.el-button`、`.el-button--primary`（组件 class）                                         |
| 错误提示     | `.van-toast__text`（Toast 提示）或 `.van-field__error-message`（表单校验） | `.el-message--error .el-message__content`（Message 组件）                                 |
| 成功提示     | `.van-toast__text`（内容通常为"登录成功"）                                 | `.el-message--success .el-message__content`                                               |
| 表格结构     | 通常为自定义 `div` 布局                                                    | `.el-table`、`.el-table__row`（Table 组件）                                               |
| 对话框       | `.van-dialog`（Vant Dialog）                                               | `.el-dialog`（Element Plus Dialog）                                                       |
| 表单校验     | `.van-field__error-message`                                                | `.el-form-item__error`                                                                    |
| 徽标/角标    | `.van-badge`（购物车数量）                                                 | `.el-badge__content`                                                                      |
| 加载状态     | `.page-loading`（自定义）                                                  | `.el-loading-mask` 或 `v-loading` 指令                                                    |

**选择器书写建议：**

- H5 端优先用语义化属性选择器（`input[placeholder='...']`、`button.sms-btn`），因为 Vant 的 class 前缀（`van-`）相对稳定。
- Element Plus 端优先用组件 class（`.el-button--primary`、`.el-table__row`），避免依赖纯文本内容，因为文案可能国际化。
- 需要按文本内容定位时，用 XPath 的 `contains(text(), '...')`，如商家端订单管理中的 `//button[contains(text(),'接单')]`。

### 11.5 WebDriver Fixture 设计

**文件路径：** `test_cases/web/conftest.py`

#### 11.5.1 两个 Fixture 的定义

```python
@pytest.fixture(scope="module")
def mobile_driver():
    """H5 手机浏览器（390×844）"""
    d = _build_chrome(390, 844, mobile=True)
    yield d
    d.quit()

@pytest.fixture(scope="module")
def desktop_driver():
    """商家端 / 管理后台桌面浏览器（1280×800）"""
    d = _build_chrome(1280, 800)
    yield d
    d.quit()
```

#### 11.5.2 两者的核心差异

| 维度            | `mobile_driver`                                  | `desktop_driver`                          |
| --------------- | ------------------------------------------------ | ----------------------------------------- |
| 分辨率          | 390×844（iPhone 14 尺寸）                        | 1280×800（标准笔记本）                    |
| Chrome 移动模拟 | `mobileEmulation`：像素比 3.0，移动端 User-Agent | 无，标准桌面 Chrome                       |
| 适用端          | H5 端（Vant 移动端组件）                         | 商家端、管理后台（Element Plus 桌面组件） |
| 触发响应式      | Vue 组件会根据 viewport 切换到移动布局           | 桌面布局                                  |

`mobileEmulation` 配置：

```python
opts.add_experimental_option(
    "mobileEmulation",
    {"deviceMetrics": {"width": 390, "height": 844, "pixelRatio": 3.0}},
)
```

`pixelRatio: 3.0` 模拟 Retina 屏的设备像素比，使 Vant 加载高分辨率图标和正确的媒体查询断点，与真机效果一致。

两个 driver 均执行 `d.implicitly_wait(0)`，彻底关闭隐式等待，强制所有元素查找使用 `BasePage` 提供的显式等待方法。

#### 11.5.3 `scope="module"` 的性能意义

pytest fixture 的 `scope` 决定 fixture 的生命周期：

| scope                | 创建时机           | 销毁时机             | 浏览器启动次数（假设10个测试） |
| -------------------- | ------------------ | -------------------- | ------------------------------ |
| `"function"`（默认） | 每个测试函数前     | 每个测试函数后       | 10次                           |
| `"module"`           | 同模块第一个测试前 | 同模块所有测试完成后 | 1次                            |
| `"session"`          | 整个测试会话开始   | 会话结束             | 1次（全局共享）                |

选择 `scope="module"` 的原因：

1. **性能**：Chrome 冷启动约 2-5 秒，一个测试模块 10 个测试用例，`function` scope 要额外花费 20-50 秒。`module` scope 只启动一次，大幅缩短总耗时。
2. **隔离性**：不使用 `session` scope，是因为 H5 测试和商家端测试需要不同尺寸的浏览器，session 级别共享会互相影响。
3. **状态污染**：模块内测试通常测同一功能域（如登录、下单），浏览器共享时测试用例应注意避免状态污染（通过 `open()` 强制导航、或在 setup 中清除 localStorage 等）。

#### 11.5.4 Headless 模式控制

```python
if config.HEADLESS:
    opts.add_argument("--headless=new")
```

`--headless=new` 是 Chrome 112+ 引入的新 Headless 实现，比旧版 `--headless` 渲染更准确（旧版 Headless 在某些 CSS 动画和 viewport 计算上有差异）。通过 `config.HEADLESS` 配置项控制，本地调试时关闭可见浏览器，CI/CD 环境开启无界面模式。

通用参数说明：

| 参数                      | 作用                                                     |
| ------------------------- | -------------------------------------------------------- |
| `--no-sandbox`            | 在 Docker/CI 容器中必须，禁用沙箱（容器内无法使用沙箱）  |
| `--disable-dev-shm-usage` | 避免 `/dev/shm` 内存不足导致崩溃（Docker 容器默认 64MB） |
| `--disable-gpu`           | 无显卡环境（如 CI 服务器）禁用 GPU 加速                  |
| `--window-size={w},{h}`   | 设置初始窗口尺寸，确保响应式布局断点正确触发             |

### 12.2 session_start_end fixture

```python
@pytest.fixture(scope="session", autouse=True)
def session_start_end():
    # === 测试会话开始 ===
    logger.info(f"测试会话开始 | 环境: {config.ENVIRONMENT}")
    logger.info(f"API URL: {config.API_BASE_URL}")
    logger.info(f"核心插件: {[p.name for p in plugin_manager.get_core_plugins()]}")
    logger.info(f"普通插件: {[p.name for p in plugin_manager.get_normal_plugins()]}")

    yield  # ← 所有测试在这里执行

    # === 测试会话结束 ===
    circuit_breaker_plugin = plugin_manager.get_plugin('circuit_breaker')
    if circuit_breaker_plugin:
        logger.info(f"熔断器状态: {circuit_breaker_plugin.get_state().value}")
        logger.info(f"熔断器失败次数: {circuit_breaker_plugin.get_failures()}")

    rate_limiter_plugin = plugin_manager.get_plugin('rate_limiter')
    if rate_limiter_plugin:
        stats = rate_limiter_plugin.get_stats()
        logger.info(f"限流统计: {stats['current_calls']}/{stats['max_calls']}")
```

**关键设计点：**

| 设计              | 说明                                                     |
| ----------------- | -------------------------------------------------------- |
| `scope="session"` | 整个 pytest 进程只执行一次（一进一出），不随每个测试重置 |
| `autouse=True`    | 所有测试自动使用，无需在每个测试函数中显式声明           |
| yield 前          | 打印环境信息、已加载插件，便于排查配置问题               |
| yield 后          | 打印熔断器/限流器统计，判断测试过程中有无服务故障        |

### 12.4 pytest_runtest_makereport — 捕获测试结果

```python
@pytest.hookimpl(tryfirst=True, hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield           # ← hookwrapper：yield 挂起，等 pytest 原始逻辑执行
    rep = outcome.get_result()  # 拿到测试报告对象

    if call.when == "call":   # 只在测试执行阶段（不在 setup/teardown）
        test_name = item.name
        if rep.failed:
            plugin_manager.execute_hook('on_test_failure', test_name, str(rep.longrepr))
        elif rep.passed:
            plugin_manager.execute_hook('on_test_success', test_name)
        plugin_manager.execute_hook('after_test', test_name, rep.outcome)
```

**hookwrapper 原理：**

- `yield` 前的代码在 pytest 原始钩子执行**之前**运行
- `yield` 之后的代码在 pytest 原始钩子执行**之后**运行
- `outcome.get_result()` 获取原始钩子的返回值（即测试结果报告）
- 通过这种方式，可以在测试结果确定后才触发插件的成功/失败钩子

## 第十四章 API 测试用例详解（test_cases/api/）

### 14.1 双模式设计规范

每个 API 测试都遵循同一个结构：

```python
def test_some_api(self, mock):
    # 准备
    client = SomeApi(token)

    if mock.use_mock:
        # Mock 模式：构造期望的响应，patch session
        resp = mock.create_mock_response(200, {"code": 200, "success": True, "data": {...}})
        with mock.mock_request(client, "post", resp):
            result = client.some_method(...)
    else:
        # 真实 API 模式：直接调用，有时需要先准备数据
        result = client.some_method(...)

    # 断言（两种模式共用）
    assert is_success(result), f"失败原因: {result.json()}"
```

**这种设计的好处：**

- 同一份断言逻辑在 Mock 和真实 API 两种模式下都验证
- Mock 模式无需后端即可 CI 快速验证
- 真实模式验证实际的后端行为

## 第十五章 UI 测试用例详解（test_cases/web/）

### 15.1 WebDriver Fixture 设计

```python
# test_cases/web/conftest.py
def _build_chrome(width, height, mobile=False):
    opts = Options()
    if config.HEADLESS:
        opts.add_argument("--headless=new")
    opts.add_argument(f"--window-size={width},{height}")
    if mobile:
        opts.add_experimental_option(
            "mobileEmulation",
            {"deviceMetrics": {"width": width, "height": height, "pixelRatio": 3.0}}
        )
    d = webdriver.Chrome(options=opts)
    d.implicitly_wait(0)  # 关闭隐式等待，全部用显式等待
    return d

@pytest.fixture(scope="module")
def mobile_driver():    # H5 手机模拟（390×844）
    d = _build_chrome(390, 844, mobile=True)
    yield d
    d.quit()

@pytest.fixture(scope="module")
def desktop_driver():   # 商家端/管理后台桌面（1280×800）
    d = _build_chrome(1280, 800)
    yield d
    d.quit()
```

**scope="module" 的性能意义：**

- `scope="function"`：每个测试启动/关闭一次 Chrome，19个测试 × ~3s = 约57s 纯浏览器开销
- `scope="module"`：每个测试文件共享一个 Chrome 实例，3个文件 × ~3s = 约9s 浏览器开销
- 节省约 48s（节约 84%）

**`implicitly_wait(0)` 的原因：**

隐式等待与显式等待（`WebDriverWait`）混用时行为不可预测，统一用显式等待可以精确控制每个元素的超时策略。

### 15.2 Auth Token 注入技术

UI 测试中，每个需要登录状态的测试如果都经过登录 UI 流程（输入手机号→获取验证码→输入验证码→点击登录），速度慢且依赖短信服务。

通过 JavaScript 直接注入 token 到 localStorage：

```python
@pytest.fixture(scope="module")
def auth(driver, base_url):
    """直接注入 token，跳过 UI 登录流程"""
    driver.get(base_url)
    # 真实模式：先通过 API 登录获取 token
    # Mock 模式：注入固定 mock token
    driver.execute_script(
        "localStorage.setItem('token', arguments[0]); "
        "localStorage.setItem('userInfo', JSON.stringify(arguments[1]))",
        token, json.dumps({"phone": phone, "role": "CUSTOMER"})
    )
    driver.refresh()  # 刷新使前端读取 localStorage 中的 token
    yield
```

**优点：**

- 测试速度快（跳过 3-5s 的登录 UI 操作）
- 不依赖短信服务和验证码
- 测试之间登录状态独立（module 级重置）

## 第十六章 已知问题清单（xfail）

### 16.1 xfail 机制说明

`pytest.mark.xfail` 标记预期会失败的测试：

- 测试确实失败 → **xfail**（期望失败，绿色，测试通过）
- 测试意外通过 → **xpass**（意外通过，黄色，表示 bug 已修复）

这种机制让已知 bug 的测试不会阻塞 CI，同时一旦后端修复，xpass 状态会提醒我们去掉 xfail 标注。

### 16.3 xpass 的处理方式

当测试从 xfail 变为 xpassed，说明后端 bug 已修复，需要：

1. 删除 `@pytest.mark.xfail(reason="...")` 注解
2. 将对应的 mock 响应从 500 改为 200（Mock 模式下维持与真实行为一致）
3. 提交代码更新

### 17.4 常见问题排查

| 问题                                         | 原因                    | 解决方案                                          |
| -------------------------------------------- | ----------------------- | ------------------------------------------------- |
| `ModuleNotFoundError: No module named 'api'` | 未从项目根目录运行      | `cd pytest-api-framework && python -m pytest ...` |
| 真实模式测试全部失败                         | 后端服务未启动          | 确认 localhost:8080 在线                          |
| UI 测试报 `SessionNotCreatedException`       | ChromeDriver 版本不匹配 | 更新 ChromeDriver 至当前 Chrome 版本              |
| 验证码错误（真实模式）                       | Redis 中无验证码        | 执行 redis-cli SET 命令写入验证码                 |
| xfail 变 xpass                               | 后端修复了 bug          | 删除对应测试的 `@pytest.mark.xfail` 注解          |
| Allure 报告无附件                            | AllurePlugin 被禁用     | 不要使用 `--disable-plugins` 参数                 |
| 浏览器弹出界面                               | HEADLESS 未设置         | 加 `--headless` 参数或设 `HEADLESS=true`          |
