## 1. 项目概述

### 1.1 框架定位

| 属性 | 值 |
|---|---|
| **框架名称** | pytest-api-framework |
| **被测系统** | TakeoutSystem 外卖点餐系统 |
| **框架类型** | 综合自动化测试框架 |
| **覆盖层级** | API + UI 双端 |
| **语言** | Python 3.11+ |
| **测试框架** | pytest 9.1 |
| **目标环境** | 后端 Spring Boot (:8080) / H5 (:3001) / 商家端 (:3002) / 管理后台 (:3003) |

### 1.2 核心设计目标

1. **接口与 UI 双端覆盖** — 同一框架同时支持 HTTP 接口测试和 Selenium 浏览器 UI 测试
2. **Mock/真实双模式** — 不依赖后端即可运行的 Mock 模式，与对接真实环境的真实模式
3. **插件化扩展** — 日志、Allure 附件等横切关注点通过插件挂载，核心代码零侵入
4. **数据驱动** — 测试数据存于 YAML，通过 `@pytest.mark.parametrize` 实现数据与逻辑分离
5. **多环境支持** — 通过配置继承体系覆盖 dev / test / staging / prod 环境

### 1.3 当前测试规模

| 测试类型 | 文件数 | 用例数 | 技术栈 |
|---|---|---|---|
| API 测试 | 4 个文件 | ~38 个 + 4 xpass | requests + Mock |
| UI 测试 | 3 个文件 | ~19 个 + 1 xfail | Selenium + Page Object |

## 3. 分层详解

### 3.1 配置层 — `config/config.py`

#### 职责
- 集中管理所有环境相关配置
- 支持多环境（dev/test/staging/prod）
- 启动时验证配置有效性

#### 继承体系

```
Config（基类：持有全部默认值）
  ├── DevConfig      — 开发调试：DEBUG 日志、60s 超时、可见浏览器
  ├── TestConfig     — 测试环境：DEBUG 日志、其余继承基类
  ├── StagingConfig  — 预发布：INFO 日志、强制无头
  └── ProdConfig     — 生产：WARNING 日志、强制 SSL 校验
```

#### 优先级链

```
环境变量（最高优先级）→ .env 文件（本地兜底）→ 代码默认值（最低优先级）
```

#### 配置验证

`Config.validate()` 在 `get_config()` 返回实例前执行统一校验，涵盖：URL 正则、超时范围、浏览器类型、环境名称。采用**错误收集策略**（非立即抛出），一次性反馈所有错误。

#### 设计评价
- ✅ 多环境继承结构清晰，子类只需声明差异字段
- ✅ 配置验证提升反馈速度，避免运行时才暴露配置问题
- ⚠️ Config 类使用类变量而非实例变量，多进程（pytest-xdist）下存在跨进程状态共享，但当前架构中这不会导致实际错误（配置进程启动时读取一次即固定）

### 3.2 API 封装层 — `api/base_api.py` + `takeout_api.py`

#### BaseApi 基类

```
BaseApi
  ├── __init__(base_url, timeout, enable_plugins, requests)
  └── 4 个 HTTP 方法
      ├── get(url)    → @allure.step("GET 请求: {url}")
      ├── post(url, json_data) → @allure.step("POST 请求: {url}")
      ├── put(url, json_data)  → @allure.step("PUT 请求: {url}")
      └── delete(url) → @allure.step("DELETE 请求: {url}")
```

**关键设计决策**：

1. **`requests` 参数注入** — 允许出入已有 `BaseRequests` 实例，配合 `http_session` fixture 实现连接池共享
2. **`@allure.step` 装饰器** — 自动生成 Allure 报告步骤节点，无需测试代码手动声明
3. **方法返回原始 response** — 所有 API 方法只返回 response 对象，不做断言（断言由测试层负责）
4. **日志自动记录** — `_log_request` / `_log_response` 统一切面日志

#### 业务 API 类 (API Object 模式)

| 类名 | 业务模块 | Token 依赖 | 方法数 |
|---|---|---|---|
| `AuthApi` | 认证（登录/登出/刷新） | 否 | 4 |
| `UserApi` | 用户资料、地址 CRUD | 是 | 7 |
| `MerchantApi` | 商家搜索、详情、营业状态 | 是 | 6 |
| `ProductApi` | 菜品菜单、分类、上下架 | 是 | 6 |
| `CartApi` | 购物车增删改查 | 是 | 5 |
| `OrderApi` | 用户下单 + 商家订单管理 | 是 | 10 |
| `PayApi` | 创建支付、查询、模拟回调 | 是 | 3 |
| `ReviewApi` | 提交评价、查看评价 | 是 | 4 |
| `CouponApi` | 优惠券列表、领取 | 是 | 3 |
| `FavoriteApi` | 收藏/取消收藏商家 | 是 | 3 |
| `HealthApi` | 健康检查（MySQL + Redis） | 否 | 1 |

**Token 注入方式**：

```python
class UserApi(BaseApi):
    def __init__(self, token: str = "", requests=None):
        super().__init__(base_url=config.API_BASE_URL, requests=requests)
        if token:
            self.requests.session.headers.update({"Authorization": f"Bearer {token}"})
```

#### 工具函数

- `is_success(response)` — 判断业务成功（支持标准 Result、健康检查、HTTP 状态码三种格式）
- `get_biz_code(response)` — 提取业务状态码（区别 HTTP 状态码与业务 code）

### 3.3 HTTP 传输层 — `common/base_requests.py`

#### 职责范围

- 封装 `requests.Session` 管理连接池
- HTTPAdapter + Retry 自动重试策略
- 插件钩子链调度中枢
- 统一响应处理（`_handle_response`）

#### 重试策略

| 参数 | 值 | 说明 |
|---|---|---|
| total | 3 | 最大 3 次 |
| backoff_factor | 1.0 | 退避时间：1s → 2s → 4s |
| status_forcelist | [429, 500, 502, 503, 504] | 触发重试的 HTTP 状态码 |
| raise_on_status | False | 不自动抛异常 |

#### 插件集成点

`_execute_with_plugins(method, url, request_func, **kwargs)` 是 HTTP 层的核心调度方法：

```
request_func() 构造
      │
      ▼
before_request 钩子 (插件链)    ← 若返回非 None，短路返回（缓存命中）
      │
      ▼
request_func()                 ← 实际 HTTP 请求（或 Mock 模式下的 session 层 patch）
      │                    \
      ▼                     ▼
after_request 钩子        on_request_error 钩子
(AllurePlugin 记录)       (错误日志)
```

### 3.4 页面对象层 — `page_objects/`

#### BasePage 基类

**设计原则**：所有等待均使用显式等待（`WebDriverWait` + `expected_conditions`），**零 `time.sleep`**。

核心方法：
- `find_element` / `find_elements` — 支持超时参数
- `click` — 等待元素可点击后执行
- `input_text` — 等待元素可见可交互后输入
- `wait_for_*` — 等待文本 / 消失 / URL 变化
- `is_element_visible` — 不抛异常的可见判断（用于断言前检查）

#### 三端 Page Object 分布

| 前端 | 页面数 | 页面列表 |
|---|---|---|
| H5 用户端 | 7 | login, home, merchant_detail, cart, checkout, order, profile |
| 商家端 | 3 | login, order_manage, shop_manage |
| 管理后台 | 4 | login, merchant_manage, order_manage, user_manage |

**共享 WebDriver 策略**：UI 测试使用 module-scoped fixture，同一文件内的测试用例共享同一个浏览器实例，避免反复启动。

### 3.5 共享工具层 — `common/`

| 模块 | 核心类/函数 | 职责 |
|---|---|---|
| `yaml_util.py` | `YamlUtil` 静态类 + `DataHelper` | YAML 加载/保存，按模块划分的业务数据访问方法，自动缓存减少 I/O |
| `mock_util.py` | `MockHelper` + `is_mock_mode()` | Mock 响应构造 + session 层 patch 上下文管理器 |
| `test_helpers.py` | `login_and_get_token()` + `TokenManager` | 统一登录（Mock 下直接返回 mock token）、多角色 Token 缓存 |
| `security.py` | `SensitiveDataFilter` + `DataMasker` | 日志中过滤 password/token/Authorization；脱敏手机号/邮箱/信用卡 |

## 4. 设计模式与核心机制

### 4.1 使用到的设计模式

| 模式 | 应用位置 | 说明 |
|---|---|---|
| **Page Object / API Object** | api/ + page_objects/ | 将业务操作封装为类方法，测试层与实现细节解耦 |
| **插件模式 (Plugin)** | common/plugins/ | 横切关注点通过钩子挂载，核心代码零侵入 |
| **模板方法** | base_api.py → takeout_api.py | 基类定义 HTTP 方法骨架，子类定义具体 API 端点 |
| **工厂方法** | config.get_config() | 根据 env 名返回对应配置子类实例 |
| **单例模式** | get_plugin_manager() | 双重检查锁定（DCL）确保全局唯一 PluginManager |
| **上下文管理器** | mock_util.mock_request() | 有限范围的 Mock 拦截，退出时自动恢复 |
| **策略模式** | 插件钩子链 | 同一钩子点按注册顺序执行多个插件策略 |

### 4.2 Session 复用机制

```
conftest.py
  └── @pytest.fixture(scope="session")
      def http_session():
          session = BaseRequests()    ← requests.Session（连接池）
          yield session
          session.close()
              │
              ▼
              注入给所有 API 类：
              AuthApi(requests=http_session)
              UserApi(token, requests=http_session)
              OrderApi(token, requests=http_session)
              ...
```

**优势**：
- 全局共享一个连接池（减少 TCP 握手开销）
- session 级别的 cookie/header 统一管理
- 插件管理器单例，日志和 Allure 记录一致

### 4.3 Mock 模式设计（session 层 patch）

```
常规调用链（无 Mock）：
  BaseApi.post() → BaseRequests.post() → _execute_with_plugins()
    → before_request → session.post() [真实 HTTP] → after_request

Mock 模式调用链（session 层 patch）：
  BaseApi.post() → BaseRequests.post() → _execute_with_plugins()
    → before_request → session.post() [patch 替换为 mock 响应] → after_request

                                     ↑
                      patch 在 requests.Session 层，
                      保留完整的插件调用链
```

**为什么在 session 层 patch 而不是 BaseRequests 层**：
- `@allure.step` 正常触发
- `before_request` / `after_request` 钩子正常执行
- AllurePlugin 正常记录请求/响应到报告
- Mock 与真实模式下的插件行为完全一致

### 5.1 API 请求完整生命周期

```
测试用例层                          API 封装层                    HTTP 传输层
─────────────                      ──────────                   ────────────

test_submit_order()
  │
  ├─ mock_helper.create_mock_response()
  │   └─ Mock 对象（状态码+JSON）
  │
  ├─ mock_helper.mock_request(api, "post", resp)
  │   └─ patch session.post
  │
  ├─ order.submit_order(...)
  │   │
  │   ▼
  │   BaseApi.post()                   BaseRequests.post()
  │   ├─ @allure.step                  ├─ 构造 URL
  │   ├─ _log_request()                ├─ 构造 request_func
  │   └─ self.requests.post() ─────►   └─ _execute_with_plugins()
  │                                       ├─ [before_request]
  │                                       │   └── LoggingPlugin (记录)
  │                                       ├─ [request_func]
  │                                       │   └── session.post() [或 Mock 响应]
  │                                       ├─ [after_request]
  │                                       │   ├── AllurePlugin (附件)
  │                                       │   └── LoggingPlugin (记录)
  │                                       │
  │   └─ _log_response() ◄───────────────┘   返回 response
  │
  └─ is_success(result) → assert
     断言业务成功
```

## 7. 插件系统

### 7.1 架构

```
get_plugin_manager() [单例工厂]
  │
  └── PluginManager [全局唯一]
      ├── plugins: Dict[str, Plugin]      ← 插件实例
      ├── plugin_info: Dict[str, PluginInfo]  ← 插件元信息
      └── hooks: Dict[str, List[Callable]]     ← 钩子注册表
           ├── before_request  → [LoggingPlugin]
           ├── after_request   → [AllurePlugin, LoggingPlugin]
           ├── on_request_error → [LoggingPlugin]
           ├── before_test     → [LoggingPlugin]
           ├── after_test      → [LoggingPlugin]
           ├── on_test_failure → [LoggingPlugin]
           └── on_test_success → [LoggingPlugin]
```

### 7.2 已注册插件

| 插件名 | 类型 | 可禁用 | 功能 |
|---|---|---|---|
| `logging` | NORMAL | ✅ | 记录请求/测试日志 |
| `allure_attachment` | NORMAL | ✅ | 自动 HTTP 请求/响应附件到 Allure 报告 |

### 7.3 插件生命周期

```
register(plugin) → on_load() → _register_hooks() → 状态: LOADED
enable(name)     → on_enable()                    → 状态: ENABLED
disable(name)    → on_disable()                   → 状态: DISABLED
unregister(name) → on_unload()                    → 移除
```

### 7.4 v2 简化

- 移除了 `PluginType.CORE` 枚举及相关逻辑（不再区分核心/普通）
- 移除了 `CircuitBreaker`、`RateLimiter`、`CachePlugin`、`MetricsPlugin`
- 当前插件系统保持了最精简的日志 + Allure 附件功能

class TestSomething:

## 9. 双模式设计

### 9.1 模式对比

| 维度 | Mock 模式 | 真实 API 模式 |
|---|---|---|
| 后端依赖 | 不需要 | 必须启动 |
| 运行速度 | 毫秒级 | 受网络影响 |
| 测试稳定性 | 完全可控 | 受外部环境影响 |
| 边界条件 | 容易构造 | 困难 |
| Allure 报告 | 完整 | 完整 |
| 集成验证 | 不验证 | 验证完整链路 |

### 9.2 前置条件策略

在测试如订单流程这类需要复杂前置状态（已支付订单、已完成订单）的用例时：

- **Mock 模式**：前置函数直接返回模拟数据，无需真实 HTTP 调用
- **真实模式**：前置函数执行真实 API 调用链路，失败时 `pytest.skip` 优雅跳过

```python
def _create_paid_order(http_session, ...):
    if config.USE_MOCK:
        return "ORD_PAID_MOCK_" + str(...)  # 直接返回模拟值
    # 真实模式：调用完整 API 链路
    order_no = _create_test_order(...)
    pay_resp = pay.create_payment(order_no, ...)
    ...
```

## 10. Architecture Review

### 10.1 优势 (Strengths)

| 维度 | 评价 |
|---|---|
| **分层清晰** | 四层架构（配置→工具→封装→测试）职责边界分明，符合单一职责原则 |
| **双模式完整** | Mock 模式下插件行为与真实模式完全一致（因 session 层 patch），Mock 结果可信 |
| **Session 复用** | session-scoped fixture 共享连接池，减少资源开销 |
| **插件解耦** | 横切关注点（日志、Allure）通过钩子注入，HTTP 引擎不直接依赖具体实现 |
| **配置集中** | 统一配置入口，多环境继承结构，启动时验证减少运行时问题 |
| **显式 Mock** | Mock 不再全局自动拦截，必须显式声明 mock_request 上下文，避免"虚假通过" |
| **封装完备** | 11 个 API 类覆盖全部业务模块，17 个页面对象覆盖三个前端 |
| **文档齐全** | api.md 对关键设计决策有详尽解释（约 450 行技术文档） |

### 10.2 可改进点 (Improvements)

#### 10.2.1 架构层面

| 问题 | 建议 | 优先级 |
|---|---|---|
| **Config 类变量设计**：Config 使用类变量 + 模块级单例，`pytest_addoption` 中直接修改 `Config.USE_MOCK` 等类属性。xdist 多 worker 下类变量共享可能导致跨进程干扰。 | 改用实例变量 + 全局配置对象（如 `@dataclass`），运行期修改通过实例方法进行 | 中 |
| **插件系统状态管理**：插件启用状态存在 `PluginInfo` 中，但 `execute_hook` 的短路语义和重试/异常处理边界不够清晰（异常时 `after_request` 不触发、但 `before_request` 已触发）。 | 明确定义异常时的钩子回调顺序（类似 finally 语义），记录文档 | 低 |
| **API 封装层对 Config 的强依赖**：`takeout_api.py` 中每个子类 `__init__` 都直接引用 `config.API_BASE_URL`，但在 `BaseApi.__init__` 中又支持 `base_url` 参数。两者冗余。 | 统一在 `BaseApi` 级别处理 base_url 默认值，子类不重复引用 | 低 |
| **MockHelper 设计冗余**：`mock_request` 中需要同时传入 `client` 和 `method`，对同一 API 对象的不同方法多次 Mock 时有重复样板代码。 | 考虑封装 mock_session 级别的方法（一次 patch 所有方法）或提供类级 decorator | 低 |

#### 10.2.2 代码质量层面

| 问题 | 建议 | 优先级 |
|---|---|---|
| **测试缺少类型标注**：测试文件大量使用 `Dict[str, Any]` 返回类型，无法利用 IDE 类型检查和自动补全 | 引入 typed-dict 或 dataclass 定义响应结构体 | 中 |
| **`is_success()` 的响应格式嗅探**：函数通过检查响应中的不同 key 来嗅探响应格式，隐式接口约定 | 定义清晰的响应 type（如 `StandardResponse` / `HealthResponse`），或让 API 方法显式指定 | 中 |
| **OrderApi 职责过重**：`OrderApi` 同时承担了用户端和商家端方法，10 个方法混在一起 | 拆分为 `CustomerOrderApi` + `MerchantOrderApi`，职责更单一 | 中 |
| **exception 处理有待强化**：`_execute_with_plugins` 中的 except 块没有进一步区分连接超时/HTTPError/JSON 解析失败 | 细化异常分类，在 BaseRequests 层提供更结构化的错误信息 | 低 |
| **魔法数字**：代码中存在如 `http_client.py` 的 `timeout=30`，`test_order_flow_api.py` 中的 `pay_type=1` 等硬编码值 | 抽取为常量或从配置/数据文件中读取 | 低 |

#### 10.2.3 测试设计层面

| 问题 | 建议 | 优先级 |
|---|---|---|
| **Mock 测试的断言空洞**：Mock 模式下测试只验证 `is_success(result)`，不验证返回数据的具体内容是否与 mock 响应一致 | 断言应验证 `result.json()` == 预设 mock 数据，确保路径正确 | 高 |
| **订单测试中真实模式的前置条件共享**：真实模式下的 `_create_paid_order` 等函数在多个测试方法间重复调用，代码重复 | 提取为 session-scoped fixture 或模块级缓存 | 中 |
| **测试数据 YAML 使用不充分**：虽然定义了 `DataHelper`，但多数测试直接在代码中硬编码 mock 响应数据 | 将 mock 响应数据也移入 YAML，实现完全的数据驱动 | 中 |
| **UI 测试缺少异常截图**：`conftest.py` 中注册了 `SCREENSHOT_ON_FAILURE`，但 BasePage 未在操作异常时自动截图 | 在 BasePage 方法中添加 try/except + allure.attach 截图 | 中 |

#### 10.2.4 工程化层面

| 问题 | 建议 | 优先级 |
|---|---|---|
| **缺少 CI 配置**：README 展示了运行命令，但没有 `.github/workflows/` 配置 | 添加 GitHub Actions 配置：Mock 模式门禁 + 真实模式 nightly | 高 |
| **缺少 pre-commit 检查**：代码风格（black/isort）没有自动化道闸 | 添加 pre-commit 配置或 CI 阶段的格式检查 | 中 |
| **缺少类型检查**：项目没有开启 mypy 或 pyright | 在 CI 中添加 mypy 检查，至少检查 common/ 和 api/ 层 | 低 |
| **xdist 兼容性**：插件系统使用全局单例，与 xdist 多 worker 不兼容 | 在 `pytest_configure` 中检测 xdist 并自动禁用插件 | 低 |

### 10.3 潜在风险 (Risks)

| 风险 | 影响 | 可能性 | 缓解措施 |
|---|---|---|---|
| **Mock 响应与真实 API 不一致**：Mock 数据可能落后于真实 API 的响应结构变化 | 测试通过但真实模式失败 | 中 | 定期运行真实模式全量回归；Mock 数据与 API 文档同步 |
| **Config.USE_MOCK 是进程级状态**：混合使用 --mock 参数和 test_data fixture，状态跟踪隐式 | 测试行为不符合预期 | 低 | 增加运行时日志输出当前模式 |
| **单模块测试过多**：`test_order_flow_api.py` 包含 16 个测试，跨 5 个模块（购物车/订单/商家订单/支付/评价） | 测试文件过大，问题定位困难 | 低 | 按业务模块拆分为独立文件 |
| **AllurePlugin 异常吞没**：插件异常被 `except Exception` 捕获并只输出 debug 日志 | 插件失效时不被察觉 | 中 | 增加 warning 日志或统计插件失败次数 |
| **UI 测试无独立测试账号隔离**：多个 UI 测试文件共用同一批测试手机号和 WebDriver | 测试间可能存在 cookie/session 干扰 | 中 | 为每个测试文件使用不同账号或 WebDriver 隔离 |

### 10.4 改进路线图建议

#### 短期（1-2 周内）

1. **高优先级 Mock 断言增强**：Mock 模式下验证 `result.json()` == 预设 mock 数据
2. **启动 CI 配置**：添加 `.github/workflows/`，Mock 模式 + 运行测试
3. **增加 pre-commit**：black + isort 格式检查

#### 中期（1 个月内）

4. **YAML 数据驱动改造**：将 Mock 响应数据也移入 YAML 文件
5. **OrderApi 拆分**：`CustomerOrderApi` + `MerchantOrderApi`
6. **UI 测试异常截图机制**：BasePage 操作异常时自动截图
7. **真实模式订单测试前置条件 fixture 化**：提取 session-scoped 前置 fixture

#### 长期（1-2 个月）

8. **Config 重构**：改为 dataclass + 实例变量，消除类变量设计
9. **响应结构类型化**：引入 typed-dict 或 pydantic models
10. **xdist 兼容性研究**：评估并实现插件系统的多 worker 隔离
